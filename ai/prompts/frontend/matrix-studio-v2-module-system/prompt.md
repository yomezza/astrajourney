# Frontend — MATRIX × STUDIO 2.0 / этап 1

Ты Frontend/UX/UI-разработчик Astra Journey; отвечаешь за веб-ассеты (vanilla JS, HTML, CSS, SVG). Репозиторий yomezza/astrajourney. Прочитай AGENTS.md, актуальный main, все документы docs/ideas/matrix-studio-v2/ из ветки docs/matrix-studio-v2-module-system и опубликованный Backend-контракт. Отдельная feature/matrix-studio-v2-frontend от свежего main; если имя занято — согласуй безопасный ref. Не merge/deploy/release самостоятельно. Не изменяй Go/SQL/серверные службы.

## Цель
Переработать архитектуру модулей Studio, не весь игровой интерфейс. APEX как референс гибкости, не копирование сложности. Сохранить палитру MATRIX, компактность, русскую I18n, SPA, Planet Mode; Chat и Notifications — старый production-стиль и полная функциональность, глобальные независимые экземпляры, не клонировать DOM/транспорт.

## Задачи
1. Аудит web/features/studio/{index,views,dashboard}.js, оконного менеджера, navigation, fleet, logistics/inventory, maps, stores и API. Зафиксируй зависимости от singleton active ship и старых окон. Не считать демо production.
2. Реестр семейств, общий resolver, независимые UUID экземпляров, lifecycle, scoped controllers, shared data/cache, два контейнера (сохранённая плитка и временное окно). Не регистрировать каждый variant как отдельный тип, не дублировать содержимое в двух контейнерах. Purpose/binding определяют функциональный подвид, размер/сетка/вкладка — UI. Повторяемые модули одного семейства в пространстве. Плавающие окна остаются при switch, исходный объект не меняется, конвертация плитка↔окно запрещена.
3. Единый каталог с двумя режимами, поиск, контекстный выбор объектов и сценариев; не показывать unsupported actions/будущие подвиды как работающие. Компактная панель вместо длинного меню; старые инструменты вне этапа доступны через адаптер/каталог, без потери функций. Флот — глобальный список/пикер, не плитка. Одно готовое стартовое пространство, не перезаписывать настройки существующих игроков; M008 до своего паспорта — совместимый текущий инструмент. Лимиты 10/16, опциональный корабль, заголовок с явным объектом.
4. M001.01: обзор, характеристики (базовые/фактические), оснащение гибрид (изображение+список, на малом размере список); сохранение раздела; заправка, переименование, установка/снятие внутри модуля. Не реализуй public/specification.
5. M002.01–03: cargo/personal/corporate, общие таблица и сетка, категории, сортировка, вместимость если применимо, удалённый просмотр, производные/фиксированные привязки; форма «Переместить» с количеством и выбором разрешённого назначения, ошибки от сервера. Межмодульный DnD отложен.
6. M003.01–02: графическая схема маршрута (не только список), редактирование промежуточных точек до серверного предела, поиск/закладки, preview, ETA/топливо/прогресс/остаток, отмена разрешённой части, локальные цели/стыковка/орбита/посадка, портал/спасение с подтверждением и стоимостью. Сохрани Planet Mode. Не заменять полноценную карту и не проектировать M004.
7. Все действия используют explicit target, не select_ship и не подмену Session.data. Не выдумывать API, цены, права или статусы. До публикации Backend-контракта допускается изолированный mock/prototype по правилам scripts/frontend-generation; production integration только после сверки DTO/ошибок. При отсутствии API сообщи блокер Backend, не делай fake success. Обработка loading/empty/unavailable/forbidden/error/stale/pending, отмена старых запросов, защита от двойной отправки, сохранение UI по экземпляру.
8. Адаптивность 320px/desktop, доступность клавиатурой, не терять нужные действия при уменьшении. Не вводить фреймворки/обязательные зависимости. Не делать отдельный WS/polling на экземпляр. Проверить сохранение геометрии, F5, несколько объектов, logout, потери прав, переход между пространствами при открытых окнах, прежние Chat/Notifications, Planet Mode, старые инструменты. Использовать реальные тесты проекта и test fixtures; не менять серверный контракт самостоятельно.

## Результат
Ветка и PR для ревью без merge. Список изменённых файлов, SHA, ссылка на использованный Backend-контракт, скриншоты/демо при возможности, фактически выполненные тесты, непройденные проверки, риски и блокеры. Не разрабатывать будущие модули/межмодульные связи/экономическую службу, не изменять игровую механику, production и релизы. Если Backend ещё не готов, отдельно сдавай изолированный прототип/архитектурную часть с точным перечнем незавершённой интеграции; не выдавай mock за рабочую игру.
