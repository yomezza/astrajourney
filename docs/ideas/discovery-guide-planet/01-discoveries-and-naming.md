# 01. Первооткрыватели и глобальные названия систем, планет, колоний

**Статус:** архитектурное предложение, не реализовано. Код изучен по main `470667919c06a871abd909dcd49213b9c67ceec4`, 13.11.2026.

## 1. Исходные факты и точка присвоения

- `universe.Star` и `universe.Planet` находятся внутри JSON `galaxies(name='Edem').data`, глобальный стабильный `Star.ID`, номер планеты `Planet.ID` уникален в системе. Звёзды других галактик имеют глобальный ID; не путать `Star.Number` с `Star.ID`. `Star.Name` и `Planet.Name` сейчас значения JSON.
- `surveys(user_id,star,source,received_at)` — факт полноценного знания системы, но `source='survey'` означает личное сканирование, другие значения могут означать полученные сведения. `research_jobs(user_id,star,scanned,total,...)` — последовательное частичное сканирование, `SystemSites()` включает планеты первыми в порядке `Planet.ID`, затем пояса и станции. `research.RevealedSites()` дополнительно показывает корпоративные станции — это **не** событие личного открытия.
- `navigation.AdvancePlayer()`: в SQL-транзакции повышает `scanned`, а при завершении ставит `INSERT INTO surveys(...,source='survey') ON CONFLICT DO NOTHING`, XP и `research_complete`, затем COMMIT. Это правильное место для системного первооткрытия.
- `worldstore.Load/LoadFrom/Commit` и `g.Revision` определяют кэш/выдачу карты; обновление одного поля БД не актуализирует уже загруженный `Galaxy`.

## 2. Игровые условия

**Система:** пользователь получает статус первого открывателя обычной системы, только если он **первым успешно завершил личное исследование системы** (`surveys.source='survey'`, новая собственная запись в этой SQL транзакции). Покупка разведданных, открытие карты, просмотр станции, получение чужих исследований и посещение сами по себе не присваивают права. Если пользователь уже получил покупные данные и позднее хочет стать первым, текущая игровая модель может запретить запуск исследования: это не обходится искусственным присвоением и требует отдельного продуктового согласования.

**Планета:** статус возникает при **первом личном серверном шаге сканирования, раскрывающем именно `planet-N`** в `SystemSites()`. При переходе `scanned old → new` выполнить обработку всех вновь раскрытых планет в той же SQL транзакции. При скачке нескольких шагов одна транзакция может раскрыть несколько планет. В случае полного завершения исследования нужно обработать диапазон `old+1..total` **до удаления** `research_jobs` — иначе потеряется событие последнего шага. Сканирование других объектов не присваивает планетных открытий. Система и её отдельная планета могут иметь разных первооткрывателей.

Две одновременные успешные операции: **один победитель на ключ (kind,star_id,planet_id)**. В обоих случаях `INSERT/UPDATE aj_discovery_objects WHERE claim_state='unclaimed'` с блокировкой строки `FOR UPDATE`/условным UPDATE и проверкой `RowsAffected()==1`. Не использовать timestamp или NATS для выбора победителя. Мутация открытия входит в прежнюю SQL транзакцию исследования: откат сканирования откатывает claim. Все записи `INSERT surveys` и `aj_discovery_objects` должны соблюдать один порядок блокировок по ключу объекта, чтобы не вызвать deadlock. Два разных пользователя могут одновременно завершить сканирование, но только первый COMMIT с успешным claim становится первооткрывателем. Контрпример с rollback победителя: следующий кандидат должен иметь возможность получить право после отката.

## 3. Хранение и общие названия

Предложенный драфт [sql/001-discoveries-and-names.review.sql](./sql/001-discoveries-and-names.review.sql):

- `aj_discovery_objects`: ключ `(kind,star_id,planet_id)`, `kind=system/planet`, `galaxy_key`, `catalog_code`, `original_name` (неизменяемое оригинальное наименование), `current_name` (каноническое глобальное имя), `name_key`, `claim_state`, `discoverer_id`, `discovered_at`, `rename_used_at`, `name_revision`, `protected_founder_key`.
- `aj_discovery_name_history`: immutable history `operation_id UUID`, actor, source=`discoverer/admin`, before/after, request_hash и timestamp; `operation_id UNIQUE` обрабатывает повтор запроса. Не хранить историю только в client.
- `aj_discovery_objects` — canonical metadata/имя, но существующий JSON мир также содержит имена. В одной Cosmic SQL tx под общим lock `784218` и world row lock обновлять registry, вложенное `galaxies.data` по стабильным ID и `Galaxy.Revision`; затем вызывать `worldstore.Commit` для инвалидации in-memory кэша. Изменение world JSON без registry запрещено по новому контракту. Добавление/удаление системы в админ-редакторе должно синхронизировать registry при той же транзакции. Удаление: `claim_state='retired'` и сохранение истории, не переназначать ID.
- Отдельный `catalog_code` не меняется после переименования. Старые гиперкоридоры, корабли, планеты, колонии, заметки, маршруты и сохранённые IDs остаются связаны с прежним числовым ID, не с именем.
- Защитить изменения мира от переноса кэша из устаревшей транзакции: новая операция идёт через существующие Global World locking и `World.Commit`. Все другие writer-пути JSON мира требуют сверки: `internal/worldstore/galaxy_management.go`, `initialization/database.go`, административный редактор; не затирать канонические имена при генерации/расширении мира.

**Названия после переименования:** космические API `/api/galaxy`, `/api/system`, `/api/state`/`expedition`, `/api/workbench`, `/api/planet/surface`, `/planet/api/v1/scene` и сохранённые label-поля должны либо читать актуальную проекцию из worldstore, либо использовать ID и получать свежую подпись. Для уже открытых окон — ревизия мира+refresh. NATS Core сигнал возможен только как hint; его потеря не должна оставлять навсегда старое имя. Нельзя перегенерировать resource/geometry seeds от имени.

## 4. Одноразовое переименование

Последовательность server-side `rename`:
1. Cookie session, допустимый request UUID, нормализация имени, rate limit; получить domain metadata и SQL tx.
2. Под установленным порядком lock world/row, проверить `discoverer_id = actor`, `claim_state='claimed'`, `rename_used_at IS NULL`, объект не protected/retired, настоящий owner аккаунта, не bot; при недопустимости — 403/409/410.
3. Сначала проверить `aj_discovery_name_history(operation_id)`: при повторе с **тем же** request_hash вернуть сохранённый результат; с другим телом — 409, не переименовывать снова. Повтор после успешного COMMIT обязан вернуть предыдущий результат даже если право уже потрачено.
4. Проверить имя и уникальность `name_key` в пределах галактики для звёзд либо системы для планет (уникальные SQL индексы). Конфликт — 409 без траты права.
5. Обновить current_name/name_key/name_revision, выставить `rename_used_at` **один раз**, сохранить `history`, атомарно обновить `galaxies.data`, увеличить world revision и COMMIT через existing World.Commit.
6. После COMMIT уведомить подключённые окна (generic cache invalidation; необязательный NATS Core). Никакого второго права при смене имени, удалении аккаунта или смене корпорации.

**Администратор** (`users.role='admin'`, серверная проверка) использует отдельную команду `admin_correct_name`, отдельный audit reason и ту же атомарную операцию с записью history; исправление не сбрасывает `rename_used_at`, не присваивает/переопределяет первооткрывателя. Модерация недопустимого имени — административный override с аудированием.

## 5. Системы корпораций-основателей

В `universe.Star.Founder` — устойчивый ключ `founder-XX` для территории; в `companies` есть `founder=true`, `founder_key` (см. schema033.sql), а `universe.FounderTerritory` и `assignFounderTerritories` назначают зоны. Администрируемые поселения и реальные станции дают дополнительные данные. **Нельзя вывести защищённость из одной близости к спиральному рукаву или только из региона.**

Предложение: брать защиту по `Star.Founder` плюс подтверждённой записи `companies(founder=true, founder_key)`. На миграции консервативно считать все непустые `Star.Founder` protected даже при временно отсутствующей компании — fail closed, выводить preflight mismatch report. Защита распространяется на все планеты защищённой системы (по умолчанию; отдельные исключения только через admin reviewed policy). Администратор задаёт имена, игрокам claim/rename недоступны. При пересчёте founder territories/статуса карты нужно атомарно пересчитать статус без сброса уже потраченных прав; правовой эффект изменения границ — отдельное решение владельца, **не** автоматический trigger из геометрии.

## 6. Легаси-данные и происхождение

- `surveys.source='survey'` и `surveys.received_at` не доказывают исторически, **кто был первым**: `received_at` мог появиться при миграции, события с разным источником и старые объекты могут не содержать достаточной истории.
- У уже завершённых исследований система получает `legacy_unattributed`, **без discoverer_id и без права переименования**. У частично открытых планет (research_jobs.scanned>=planet.ID), завершённых surveys и существующих planet_surfaces — тоже `legacy_unattributed`; старые непросканированные планеты могут остаться `unclaimed`. Данные backfill определяются реальными `Planet.ID` и snapshot, а не случайным игроком.
- Для исторически unclaimed систем/планет первый **будущий** личный completion/planet-scan может выдать claim. Для legacy-unattributed — только ручная админ-реконструкция с подтверждёнными доказательствами, по отдельной review-процедуре; не вручать первый статус автоматически тому, кто открывал первым после релиза.
- Продавец разведданных **не** становится первооткрывателем и получатель разведданных **не** становится первооткрывателем. Исторические исключения фиксировать отдельно, не переписывая общий инвариант.

## 7. Политика названий — предложено к согласию

- Системы: 3–40 графем; планеты 3–40; колонии 3–60. NFKC, trim, collapse whitespace, запрет bidi controls, невидимых/управляющих символов, суррогатов, URL, HTML, emoji-only и служебных имен. Разрешены буквы всех языков, цифры, пробелы, обычные дефисы, апострофы, точки; не запрещать кириллицу.
- `name_key`: один проверяемый Unicode casefold/NFKC/whitespace normalizer на Go; SQL UNIQUE index по записанному ключу. Для legacy seed SQL lower(trim) — **нужна пересверка** до открытия rename API. Не опираться на collation-dependent `lower()` как на полное Unicode casefold.
- Уникальность: для системы — внутри одной галактики; для планеты — внутри одной системы; колонии — в пределах поверхности или конкретного поселения по согласованию. UI всегда показывает стабильный каталожный код рядом с пользовательским названием. Резервные имена и нежелательное содержание — собственный versioned moderation список, серверная проверка и report/админ correction, без внешнего модерационного сервиса.
- Имя менять при любом повторе только с отдельным действующим правом; при отбрасывании нарушающего имени админом не выдавать новое «одноразовое» право без решения владельца.

## 8. Переименование колоний — отдельная механика

`planet_colonies` — завершённая колония с `id,project,surface,sector,owner_user,owner_company`; `planet_projects` хранит инициатора и имя проекта, но у колонии **нет отдельного имени**. Поэтому добавить отдельную `aj_colony_names(colony_id FK...ON DELETE RESTRICT, current_name, name_key, revision, updated_at)` и историю изменений; не писать имя поверх `planet_projects` как будто это owner identity. Для проекта до завершения сохранять его прежнее `planet_projects` имя; после completion колония получает своё имя при первой пользовательской смене (default label из проекта).

Право: personal owner `owner_user=actor` или corporate owner (проверка текущего `company_id` и `CompanyAccess(...,'colonize')`/право manage), admin correction; обычный участник корпорации не может. При смене владельца история сохраняется, новое полномочие определяется **только** текущим owner, старый владелец утрачивает управление. Предлагаем cooldown **24h** между пользовательскими переименованиями (админ correction вне cooldown) и историю без срока потери; временные параметры требуют согласования. При завершённой корпорации/удалении поверхности следовать действующему проектному delete/reset, ничего не каскадировать молча. На картах и в Planet показывать имя по `colony_id`, не передавать его вместо `surface/sector`.

**SQL для review:** [sql/005-colony-names.review.sql](./sql/005-colony-names.review.sql) содержит отдельное имя завершённой колонии, историю, уникальность имени в пределах поверхности и составной внешний ключ. Перед внедрением требуется проверка на тестовой PostgreSQL и согласование поведения при удалении поверхности.

## 9. Точки тестирования

Тестировать на disposable TEST_DATABASE_URL, не production.
