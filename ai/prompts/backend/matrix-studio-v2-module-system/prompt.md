Ты Backend-разработчик Astra Journey (Go, PostgreSQL, службы). Репозиторий yomezza/astrajourney. Владелец согласовал продуктовые требования и поручает подготовить серверную часть новой модульной системы. Каноническая спецификация находится в ветке docs/matrix-studio-v2-module-system, каталог docs/ideas/matrix-studio-v2/ (README, ARCHITECTURE, CONTEXTS, MODULE-REGISTRY, MODULE-LIFECYCLE, DEVELOPMENT-RULES, DECISIONS и три паспорта). Прочитай ВСЕ файлы, AGENTS.md и актуальный main. Работай в отдельной feature/matrix-studio-v2-backend от свежего main, не в docs-ветке. Если имя занято — согласуй безопасный отдельный ref. Не merge/deploy/release без владельца.

## Задачи
1. Аудит существующих workspaces, UUID ownership/revision, JSONB, DTO, migration runner, API gateway и игрового command routing. Проверь текущие PR и расхождения с baseline; не предполагай отсутствие явных ship_id там, где они уже есть.
2. Спроектируй и документируй единый серверный контракт семейств, purpose, binding, допустимых подвидов/размещений, UI settings. 1–10, 16, опциональный контекст, повторяемые экземпляры, fixed/derived/global/workspace. Сохрани защиту 64 KiB или обоснуй изменение, ACL, UUID, ревизии. Никаких отдельных таблиц на каждый вид без обоснования. Новые workspace contexts кроме ship не вводить. Временные окна не входят в layout.
3. Совместимая миграция старых раскладок (fleet/overview/cargo/map и legacy operations/market/mining), сохранение IDs/геометрии/привязок, stale refs, старый Web и безопасный rollout/rollback. Предложи карту миграции до реализации, не удаляй пользовательские настройки. Не трогай production DB.
4. M001.01: явные адресные чтения/команды корабля, базовые/эффективные характеристики, переименование, заправка с реальной стоимостью/количеством, оборудование и совместимость. Не реализуй public/specification.
5. M002.01–03: cargo, personal, corporate. Адресные данные и доступ, удалённый просмотр, текущая/фиксированная станция, реальные остатки/ёмкости/категории, атомарное перемещение с проверкой обеих сторон, ролей, местоположения, резерва, вместимости и гонок. Не внедряй новое производство, удалённую телепортацию грузов или будущие хранилища.
6. M003.01–02: фактический preview/запуск маршрута, до 20 точек, ETA/топливо/резерв, состояние перехода, отмена оставшихся точек, локальные перемещения, стыковка, орбита, посадка, портал, спасение с реальной стоимостью. Используй существующую игровую семантику; explore не заменяет route. Не реализуй новые правила перелётов.
7. Для каждого чтения и команды — explicit target, проверка ownership/ACL/актуального состояния в транзакции; не использовать select_ship как prerequisite, не подменять server active ship. Если права потеряны, безопасная ошибка без утечки. Никаких выдуманных полей/расчётов. Согласуй контракт с Frontend до подключения; документируй endpoints/DTO/status/errors, examples, fixtures, capability semantics, versioning и миграцию в своей ветке. Frontend отвечает за web assets: не переписывай их в этом PR.
8. Тесты новой и существующей БД, revision/UUID/ACL/concurrency, команды A/B, повтор запросов, отсутствие побочных эффектов, навигация/инвентарь и совместимость старого клиента. Сверь DEVELOPMENT-RULES и паспорта. Не добавляй Economy, межмодульные события, будущие семейства, новые обязательные службы/зависимости.

## Результат
Опубликуй ветку и PR на main для ревью (без merge). Отчёт: SHA, список файлов, контракт и его ссылка, миграция/rollback, реальные тесты и непроверенное, риски, блокеры и точная инструкция Frontend. При недостающей механике зафиксируй gap, минимальное предложение и необходимость согласования, не объявляй готовность без проверки. Не меняй production, конфиги/секреты или релизные артефакты. Сначала публикуй контракты, чтобы Frontend мог параллельно готовить архитектуру.
