# Единый командный терминал Astra Journey

Интеграционная ветка основана на `main` и включает PR №16, в который уже вошли изменения PR №15. PR №10 описывает первоначальный контракт рабочих пространств. Game API — имя игровой службы в этом документе. Совместимые ключи TOML, бинарник Cosmic и контракт `astra-api-v1` сохраняются.

## Контекст и данные

Сессия задаёт аккаунт и права, пространство задаёт корабль по умолчанию, экземпляр модуля хранит собственную привязку и представление. Существующие режимы `workspace`, `fixed` и `none` сохраняют своё значение. Просмотр объекта относится к интерфейсу. Команда указывает корабль явно и проходит серверную проверку. Отозванная привязка требует выбора объекта игроком. Общие Chat и Notifications принадлежат сессии. Переключение пространства меняет раскладку и контекст чтения.

Общий снимок сессии остаётся источником сведений об аккаунте и флоте. Контекстные сведения кораблей разделяются по ID, ожидающие чтения переиспользуются карточкой и её окном, а ответы старой сессии отбрасываются. Workbench пока сохраняет on-demand продвижение симуляции.

## Матрица начала интеграции

| UI | Чтение | Цель команды | Правило обновления |
| --- | --- | --- | --- |
| Станционный рынок STUDIO | `GET /api/expedition?ship=ID` | Корабль, система, станция, ресурс, количество и подтверждённая цена | Подтверждённая сделка обновляет рынок, груз, баланс и историю через снимок сессии |
| Проверка сделки | `GET /api/expedition/commands/{id}` | Квитанция текущего аккаунта | При найденной квитанции обновляется снимок сессии |
| Раскладка | `/api/workspaces` | Пространство, экземпляр, ревизия | Сохранение относится к раскладке |

## Журнал станционных сделок

Прежний POST Expedition принимает совместимое необязательное поле `request_id` для покупки или продажи с явным кораблём и ценой. Запись квитанции входит в транзакцию со списанием кредитов, изменением груза и запасов. Повтор с тем же содержимым возвращает сохранённую квитанцию. Повтор с другим содержимым возвращает `ACTION_ID_REUSED`. Проверка выполняется под имеющейся блокировкой аккаунта до проверки текущего положения корабля, поэтому подтверждённая сделка доступна и после его перемещения. Порядок существующих блокировок сохранён.

Поле `error` сохраняет читабельную строку. Новые сценарии используют `code`, в том числе `MARKET_PRICE_CHANGED`, `SHIP_CONTEXT_CHANGED`, `SHIP_RESERVED`, `SHIP_IN_TRANSIT` и `ACTION_REJECTED`. Отсутствие квитанции `ACTION_UNCONFIRMED` означает неопределённый результат. После обрыва связи вкладка сохраняет подтверждённый запрос на время сессии браузера. Игрок может проверить квитанцию или повторить тот же запрос с прежним ID. Возобновление сделки по обновлённой цене требует отдельного подтверждения.

## Подтверждённые проблемы

- `internal/terminal/expedition.go`, `Expedition`. После списания сервер ещё собирал большой ответ Expedition. Если ответ терялся, вкладка могла инициировать новую покупку. Для станционных команд с ID предусмотрены транзакционная квитанция и её чтение.
- `web/features/studio/dashboard.js`, `marketReading`. При изменении котировки открытое подтверждение содержало старое предложение. После отказа по цене обновляется снимок, черновик количества остаётся в карточке.

## Совместимость и установка

Старый Web продолжает использовать прежний POST без идентификатора. Для нового рынка STUDIO нужен Game API с миграцией `schema_expedition_commands.sql`. Проверять раздельную установку следует в тестовой среде. Сначала Game API применяет миграцию при старте, затем служба Web активирует ZIP из того же коммита. Откат интерфейса выполняется активацией предыдущей ревизии Web согласно [инструкции установки](../operations/web.ru.md). Сохранённые квитанции остаются доступны при повторном обновлении.

## Открытие инструментов и восстановление раскладки

`openIntent` в `web/features/shell/module-routes.js` получает тип модуля, область, цель, представление и правило переиспользования. Диспетчер передаёт рабочие контексты STUDIO. Каталог сохраняет обычный поиск и принимает команды `SHIP 102`, `CARGO 102`, `SYSTEM 2`, `MARKET 102`, `TASKS 102`. Команда без ID предлагает доступные корабли. Ссылка из уведомления и кнопка «Открыть трюм» используют точный ID. Чтение цели не выполняет серверную команду выбора корабля.

Для карты, рынка, логистики, исследований и задач расширен допустимый набор привязок layout v1. Для ранее сохранённых карточек этих типов `none` продолжает означать следование контексту пространства. Типы `fleet`, `cargo` и `mining` сохраняют независимый режим без корабля. Наличие корабля и его принадлежность проверяются при сохранении и отдельно в игровом API.

При конфликте серверного номера ревизии пользователь может заново загрузить серверную раскладку или явно повторить собственные изменения поверх неё. Алгоритм сравнивает исходную, локальную и серверную версии. Независимые поля объединяются, а несовместимые правки порядка, привязки и конфликт редактирования с удалением оставляют локальный черновик. Совмещённая раскладка снова проходит проверку актуальной ревизии сервером.

## Расширенная матрица маршрутов

| Инструмент | Источник и команда | Текущий уровень интеграции |
| --- | --- | --- |
| Флот и оснащение | `GET /api/fleet`, `GET /api/ship/modules`, команды существующего игрового API | Флот доступен в STUDIO. Полное оснащение работает в прежнем модуле |
| Система и навигация | `GET /api/galaxy`, `GET /api/system`, команда навигации Expedition | Система открывается по точному ID. Прокладка полного маршрута доступна в основном атласе |
| Локальная логистика | `GET /api/workbench`, `POST /api/logistics` | Фиксированный источник, личный склад или собственный корабль у той же станции. Пакет ресурсов проходит существующую транзакцию с `request`. При потере ответа сохраняются источник, назначение и тот же ID |
| Рынок игроков | `GET/POST /api/market/global`, `POST /api/workbench` | Глобальный рынок и ордера работают через существующие представления |
| Планировщик | `GET/POST /api/planner` | Независимые окна используют прежний компонент с привязанным кораблём |
| Финансы и профиль | `GET /api/profile`, `GET /api/workbench` | Финансовая история открывается из каталога и команды `FINANCE` |
| Корпорации и колонии | `GET/POST /api/companies`, `GET /api/planet/projects`, `GET /api/planet/project`, `POST /api/planet/action` | Подключены действующие экраны аккаунта и планетарных объектов |
| Связь и планета | `GET/POST /api/notifications`, транспорт Chat, `/api/planet/handoff`, `/api/planet/visit`, `/api/planet/return` | Уведомления открывают объект по ID. Существующие интерфейсы Chat, Notifications и переход на планету используются в браузерной интеграции |

В панели администрирования игровая служба отображается как **Astra Journey Game API** с прежним идентификатором `cosmic` для клиентов мониторинга.

## Локальная сборка

Использовать компилятор Go из `go.mod`. Для тестовой пары собрать бинарник и Web ZIP из одного коммита.

```bash
mkdir -p /tmp/unified-terminal
go build -trimpath -o /tmp/unified-terminal/astra-journey-linux-amd64 ./cmd/astra-journey
go run ./cmd/astra-web-assets -root web -out /tmp/unified-terminal -tag v0.31.6
python3 scripts/verify-web-release.py v0.31.6 --directory /tmp/unified-terminal
```

Здесь `v0.31.6` — метка тестового ZIP. Для запуска на тестовом стенде сначала подключить собранный Game API к тестовой базе, затем остановить Web и установить ZIP через `--install-pack` со штатным `CONFIG_FILE`. Ручная установка использует `[web].sync_enabled = false`. Сверить `revision` в `/web/api/v1/health/ready` с `astra-journey-web.json`.

| Комбинация | Поведение |
| --- | --- |
| Прежний Web и новый Game API | Старый формат Expedition без ID команды и прежние маршруты остаются доступны |
| Новый Web и новый Game API | Доступны подтверждённые станционные сделки и дополнительные привязки |
| Новый Web и прежний Cosmic | Для станционных сделок STUDIO требуется признак `station_trade_receipts` в `GET /api/state`. Обновление backend должно предшествовать установке нового Web |
| Откат Web при работающем новом Game API | Активировать прежнюю ревизию ZIP с прежним хранилищем. Дополнительную таблицу квитанций сохранять для дальнейшего обновления |

Среди оставшихся этапов — полный перевод игровых экранов на независимый предметный store, дистанционный просмотр предложений с контекстом станции, полные операции оснащения и планировщика, паспорт производительности и общий сценарий с тремя кораблями.
