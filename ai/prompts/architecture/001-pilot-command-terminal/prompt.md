## Цель постановки

Проверить, как реализовать **изолированный frontend-прототип** командного терминала с вкладками персональных рабочих пространств.

В каждом пространстве выбирается свой корабль. Два разных объекта с одинаковым названием («Пилигрим», mock ID 41 и 82) не должны смешиваться при отображении «Корабля», «Трюма» и «Добычи».

## Что нужно было исследовать

- `internal/server/web/ui/windows.js`: глобальный реестр `Modules` и ID окон.
- `internal/server/web/features/fleet/`, `features/mining/`, `features/workspace/`: привязка к `Session.data.expedition`, селекторы и действия.
- `internal/server/web/core/preferences.js`: безопасное локальное сохранение per-account.
- `scripts/frontend-generation/`: изолированный mock-стенд без настоящих игровых команд.
- Раздельные `workspaceId` / `moduleInstanceId`; `workspace` / `fixed` / `none` контексты.
- Граница между локальным просмотром другого корабля и **командой серверу**, которую нельзя перенаправлять не тому кораблю.
- Восстановление вкладок, размеров и безопасного UI-состояния, проверки недоступных объектов и ролей.

## Границы

Не изменять production-окна, Go, API, PostgreSQL, пользовательские данные и релизный конвейер; не считать прототип рабочей механикой.

## Результат

Архитектурное приложение **уже опубликовано** по ссылке выше. Именно оно, а не этот промпт, — источник технических рекомендаций для frontend. Не повторять проектирование, пока не возникнет новое поручение или подтверждённый конфликт с актуальным кодом.

Если пользователь отдельно поручит перепроверку, актуализировать анализ по новому `main` и подготовить отчёт с реальными путями/коммитами.
