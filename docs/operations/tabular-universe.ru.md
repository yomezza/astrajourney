# Табличное хранение мира · 0.26.0

Системы, планеты и гиперкоридоры больше не хранятся внутри общего
`galaxies.data`. Существующая строка `name='Edem'` сохраняется как архив
до переноса; после успешной миграции записи в неё блокируются триггером.
Рабочие чтения и изменения используют таблицы. Регенерация исправного
существующего мира для переноса не выполняется. Ранее существовавшие
версионные обновления старых миров сохраняются в штатном startup runner.

## Таблицы и ключи

| Таблица | Назначение |
| --- | --- |
| `universe_state` | Формат хранения 1, версии генератора, ревизия мира, токен кэша, служебные параметры и SHA-256 архивного источника |
| `galaxy_catalog` | Стабильный текстовый ID галактики, название, seed, форма, параметры и состояние |
| `system_identity` | Глобальный числовой ID системы, постоянный UUID, принадлежность галактике |
| `star_systems` | Строка системы, типизированные координаты/класс/название и JSONB дополнительных характеристик |
| `system_planets` | Строка планеты, постоянный UUID, числовой ID внутри системы, типизированная орбита/масса/температура и JSONB атмосферы/ресурсов/расширений |
| `universe_lanes` | Рёбра навигационного графа |
| `universe_regions` | Определения регионов |

Числовые ID не перенумеровываются и не заменяются UUID в существующих кораблях,
заданиях, колониях и поверхностях. Сохраняются пары `(star, planet)`, каталоговые
коды, имена, seed, закрытые данные геологии, открытия и история переименований.
Удалённые системы остаются tombstone-записями. UUID назначается один раз,
загружается при следующем запуске и защищён от изменения триггером.

`star_systems` использует **PARTITION BY LIST (galaxy_id)**. При создании
галактики Cosmic создаёт её секцию в той же транзакции; названия секций
получаются из хэша стабильного ID и безопасно квалифицируются схемой.
Переименование галактики не перемещает строки и не создаёт новую секцию.
Секции удалённых галактик сохраняются вместе с историческими ID.

PostgreSQL требует включать ключ секционирования в уникальные ограничения
секционированной таблицы. Поэтому глобальная уникальность ID/UUID системы
обеспечивается `system_identity`, а PK данных — `(galaxy_id,id)` с FK на реестр.
UUID планет уникальны в `system_planets`, числовая связь — `(system_id,id)`.
Планеты сейчас хранятся в отдельной обычной таблице; LIST-секции нужны системам.

Индексы: PK/FK и уникальные UUID, активный номер системы в галактике, активный
регион галактики, планеты по системе/порядку, оба конца коридора. Существующие
индексы канонических имён в `aj_discovery_objects` сохраняются. Общий GIN на
все JSON-атрибуты не добавляется: для конкретного поиска нужен отдельный
измеренный запрос. Галактика в условии запроса позволяет отсекать секции;
одна только UUID-идентификация не означает автоматического ускорения всех запросов.

## Запись и переименование

UI передаёт `object.uuid` для переименования. Сервер разрешает UUID в прежние
числовые связи, проверяет вид объекта и отвергает противоречащие ID. Старый
запрос с `star_id/planet_id` продолжает поддерживаться. Права, одноразовое
переименование, Unicode-нормализация, причина исправления администратора,
идемпотентность и история сохраняются. В новых квитанциях истории есть UUID.
При переименовании планеты также обновляется название её сохранённой поверхности.

Переименование изменяет строку выбранной системы/планеты и маленькую строку
ревизии; вся галактика не сериализуется и не записывается. Редкие массовые
операции администратора сравнивают системы/планеты с предыдущим состоянием,
пишут изменившиеся строки ограниченными pgx-пакетами и обновляют граф при
его изменении. Дополнительные ключи JSONB сохраняются при обновлении объекта.
Неизвестные расширения исходного JSON переносятся в `details` соответствующего
объекта; расширения метаданных мира — в `universe_state.details`.

Кэшем остаётся неизменяемый снимок мира в памяти: алгоритмы маршрутов продолжают
использовать совместимую Go-модель с прежними ID. При холодной загрузке таблицы
читаются пакетно, без запроса на каждую звезду. У обычных читателей — единый
MVCC-снимок; для переданного READ COMMITTED transaction проверяется токен до/
после чтения и смешанный снимок повторяется. Транзакции не занимают второе
соединение пула. Полная ленивая загрузка отдельных систем во всех игровых
подсистемах не является частью этой миграции.

## Предварительная проверка без записи

Новый Cosmic поддерживает `--check-universe`. Режим использует существующий
TOML/окружение, открывает PostgreSQL **READ ONLY**, выводит только тип хранилища,
количество галактик/систем/планет/коридоров и счётчики неверных ссылок. Не создаёт
таблицы, разделы, учётные записи и мир; не запускает HTTP и симуляцию.
Seed, ключи, пароль, DSN, cookies и токены в отчёт не входят.

Linux:

```bash
CONFIG_FILE=/etc/astra-journey/shared.toml ./downloads/astra-journey-v0.26.0-linux-amd64 --check-universe
```

Windows PowerShell:

```powershell
$env:CONFIG_FILE = 'C:\AstraJourney\shared.toml'
.\astra-journey-v0.26.0-windows-amd64.exe --check-universe
```

`ready: true` означает, что структурная проверка и перечисленные проверки ссылок
пройдены; финальная миграция дополнительно выполняет существующие проверки
имён и версионных обновлений, сверку данных и валидацию FK.

## Порядок обновления и миграция

1. Сохраните согласованную резервную копию PostgreSQL и файлов данных служб.
   Остановите старые службы перед фактическим переносом.
2. Сохраните прежний TOML, `database.schema`, права роли, пути файлов и erasure
   journal Chat. Проверьте новый Cosmic с `--check-universe`.
3. Запустите Cosmic 0.26.0 под прежней ролью миграций с правами DDL в игровой
   схеме. Он создаст таблицы и секции, перенесёт данные, назначит UUID и сверит
   Go-представление всех систем, планет, коридоров и метаданных до COMMIT.
4. В той же транзакции проверяются/добавляются FK кораблей, станций, обзоров
   систем (`surveys`), реестра открытий и планетарных поверхностей.
   Неверная ссылка прерывает перенос; данные не исправляются автоматически.
5. После успешного старта Cosmic проверьте `--check-universe` ещё раз:
   тип хранилища должен быть `tabular`. Запустите Planet и при необходимости Chat,
   затем обновите вкладку браузера.

DDL: [schema.sql](../../internal/universestore/schema.sql).
Перенос и сверка: [store.go](../../internal/universestore/store.go),
[legacy_extras.go](../../internal/universestore/legacy_extras.go).
FK: [references.go](../../internal/universestore/references.go).
Оркестрация — [database.go](../../internal/initialization/database.go).

Все стадии миграции входят в startup-транзакцию Cosmic под существующими
блокировками мира. Ошибка откатывает новые данные и DDL; повторный запуск
использует прежний источник. После успешного переноса следующие старты читают
таблицы, а архив не используется как актуальное состояние. Planet/Chat не
выполняют этот перенос; планетарная схема остаётся 10.

**Откат:** старый бинарник не умеет читать новую модель и не может записать
архив. Для отката после первого нового изменения восстановите согласованный
backup всей БД и файлов до миграции. Переключение одной таблицы или копирование
архивного JSON поверх нового мира потеряет последующие изменения и не считается
корректным откатом. Старые опубликованные версии/сборки не удалялись.

## Проверено

* Перенос мира с 3000 системами, отдельными планетами и планетарной поверхностью:
  содержимое, расширения JSON, архив/его SHA, имущество, повторный запуск и UUID.
* Отказ и полный rollback при неверной ссылке корабля; read-only preflight и
  настоящий запуск `--check-universe` без изменения ревизии или пользователей.
* Ручная интерференция COMMIT между чтением систем и планет: смешанный снимок
  повторяется и возвращает согласованные данные.
* Переименование планеты по UUID, идемпотентность, неверная пара UUID/ID;
  `xmin` системы и другой планеты не меняется. UUID защищены от UPDATE.
* Создание новых секций: 5 и 50000 систем, административное preview/apply,
  старые миграции, сохранение имущества, портал и навигация.
* Настоящий Chromium: создание галактики, desktop/narrow UI и переименование
  через форму с UUID; Planet: строительство, расчистка, общее состояние двух
  аккаунтов, checkpoint/resume на расчищенной площади.
* Кэш с малым/занятым пулом и собственным transaction connection, race и go vet.
  Windows сборки кросс-компилируются; непосредственно на Windows не запускались.

Проверки выполняются на изолированной PostgreSQL 17. Рабочая БД владельца
автоматически из облачной среды не изменяется; её перенос начнётся при запуске
нового Cosmic по описанному порядку.
