# Cosmic/Planet 0.25.0: обновление, база знаний и возврат с поверхности

Это инструкция к реализованному выпуску, а не SQL review. Cosmic 0.25.0 и Planet 0.25.0 используют планетарную схему **8**; Chat остаётся 0.24.14. Рабочие БД и конфиги при разработке не изменялись.

## Обновление существующей установки

1. Сделайте резервную копию PostgreSQL и существующих файлов данных служб. Сохраните прежние `database.schema`, строку подключения, конфиг и пути Chat/Planet.
2. Остановите Cosmic и Planet. Замените **обе** службы сборками своей ОС из релиза 0.25.0; не оставляйте старый Planet рядом с новым Cosmic.
3. Запустите Cosmic под прежней ролью, имеющей права на его миграции. Он применяет `schema250.sql`–`schema254.sql` своим штатным runner и заполняет реестр объектов **после** загрузки/создания галактик. Вручную выполнять review SQL из `docs/ideas/` не надо.
4. Если Planet использует отдельную ограниченную роль, после миграции выдайте ей права на две новые таблицы, указанные ниже. Запустите новый Planet и проверьте «Статус служб».
5. Перезагрузите вкладку игры. Активная высадка восстанавливается по серверному визиту. После выхода из аккаунта персонаж остаётся на поверхности и продолжает высадку при следующем входе.

Новые системы/планеты получают стабильные каталожные коды. Исторические знания не превращаются в права случайного первооткрывателя. Если старые названия конфликтуют после Unicode-нормализации, Cosmic прерывает и откатывает стартовую транзакцию с `discovery preflight: duplicate canonical name`; исправление реальных данных требует отдельного решения владельца. Автоматически менять чужие имена или удалять данные нельзя.

Нормальный возврат теперь требует исходного посадочного модуля: остановитесь в пределах **5 игровых единиц от входа**, нажмите модуль и «Вернуться на корабль». Разрешение живёт **30 секунд**, привязано к визиту/координатам/поколению/fence и расходуется один раз. Прямой HTTP return и старый WS `leave` больше не обходят эту проверку. В соседнем секторе чужой модуль не является исходной точкой возврата.

Аварийное восстановление доступно только при подтверждённой сервером неисправности: старый визит, просроченная аренда runtime, исчезновение исходной посадки либо проверенная ошибка данных сцены. Задержка сети сама по себе не даёт свободного возврата. Операция записывается в `admin_log` как `planet_emergency_recovery`.

## Права ограниченной роли Planet

Выполняет DBA **после Cosmic migration runner**, с прежней схемой в `search_path`. Здесь `planet_runtime` — пример имени роли, а не обязательное переименование вашей роли:

```sql
BEGIN;
-- Пример: SET LOCAL search_path TO cosmosimulator, pg_catalog;
GRANT SELECT, INSERT, UPDATE
  ON aj_planet_return_authorizations TO planet_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE
  ON aj_planet_recovery_diagnostics TO planet_runtime;
COMMIT;
```

Права на прежние runtime/character/visit таблицы сохраняются. Planet не получает DDL, не создаёт схемы и не мигрирует БД. Chat новые таблицы не использует. Пример подключения к БД из старой установки сохраняйте, включая её имя и схему.

## Изображения руководства

Для Cosmic можно добавить в существующую секцию, не создавая второй `[cosmos]`:

```toml
[cosmos]
# Остальные параметры службы остаются прежними.
guide_media_dir = '/var/lib/astra-journey/guide-media'
```

Для Windows допустим TOML literal path, например `'D:\astrajourney\data\guide-media'`. В режиме переменных окружения используется `GUIDE_MEDIA_DIR`; без параметра — `data/guide-media` относительно рабочего каталога Cosmic. При TOML-режиме действуют прежние правила выбора конфигурации. Не направляйте webroot на этот каталог. Учётной записи Cosmic нужны чтение, создание, атомарное переименование и удаление файлов здесь.

Загрузку выполняет администратор из «Управление базой знаний». Поддержаны статичные PNG/JPEG/WebP до **8 MiB**, не больше **4096 × 4096**. Файл проверяется декодером и перекодируется в PNG; расширение исходного имени не определяет тип. Не более двух параллельных обработок. Загруженный SVG получает **415**: безопасного sandbox rasterizer в текущей сборке нет. Встроенные игровые SVG доступны отдельно по проверяемому manifest key.

Файлы имеют UUID-имена, метаданные и SHA-256 хранятся в PostgreSQL. Протокол записи: private staging → fsync → `pending` в БД → atomic rename → `ready`. Публичная выдача требует `ready` и ссылки из опубликованной доступной статьи; администратор также может посмотреть неопубликованное изображение. Raw HTML/SVG не публикуется.

Обслуживание запускается в Cosmic при старте и затем раз в час, с ограничением 30 секунд и до 200 очередных проверок содержимого за проход. Проверенные записи перемещаются в конец очереди. Совпавший с SHA файл `pending` восстанавливается в `ready`; отсутствующий/повреждённый `ready` и безфайловый `pending` старше суток попадают в `quarantined`. Ошибки обслуживания отражаются в журнале Cosmic. Старые staging/orphan файлы удаляются после суток. Явно удалённые, не связанные ни с одной редакцией изображения физически удаляются через **30 дней**; их метаданные сохраняются. Неиспользуемый `ready` автоматически не удаляется.

Ссылки **всех** редакций, включая старые, блокируют удаление медиа. Архивирование/снятие публикации не удаляет историю. Удалённый встроенный asset показывает «Ресурс недоступен», а не произвольный запасной URL.

## Согласованный backup и восстановление

1. Для простой согласованной копии остановите Cosmic, чтобы прекратить CMS-записи и GC; для полного игрового снимка остановите также писателей Planet/Chat.
2. Сохраните PostgreSQL штатным `pg_dump` или согласованным физическим backup. Одновременно скопируйте **весь** `guide_media_dir`, включая UUID-файлы; зафиксируйте дату, схему, версию служб и SHA-256 копии. Не сохраняйте пароли в отчёте.
3. Восстанавливайте БД и media из **одной контрольной точки**, с тем же владельцем файлов. До старта игроков проверьте UUID/размеры/SHA-256 по `aj_guide_media`; не подменяйте отсутствующее изображение файлом с тем же именем.
4. После восстановления запустите Cosmic: сканер проверит очередную порцию записей. Для больших архивов проверьте все SHA отдельно до запуска; один проход сканера намеренно ограничен. Недоступное изображение показывается заглушкой, а не нарушает чтение статьи.

Не выполняйте автоматический downgrade путём удаления новых таблиц/истории. Перед откатом версий остановите обе службы и подготовьте совместимое восстановление из согласованной копии: старый протокол возврата несовместим с защитой 0.25.0.

## Работа редактора

Категории имеют до трёх уровней, порядок, RU/EN, `visible/hidden/archived`. Удаление непустой категории запрещено; сначала перенесите статьи/дочерние категории либо архивируйте ветку. Каждое сохранение статьи создаёт неизменяемую редакцию выбранного языка. Публикация — отдельное действие; RU и EN публикуются независимо. Если EN-публикации нет, читатель получает целую русскую публикацию с отметкой RU.

При конфликте версии редактор сохраняет введённый текст, показывает серверную ошибку и актуальную версию; загрузка чужой актуальной правки требует явного решения редактора. Восстановление старой редакции создаёт новую. Скрытие, архивирование и снятие публикации сохраняют историю.

Примеры безопасных ссылок в Markdown: `[Железо](game:resource:iron)`, `[Статья](article:UUID)`, `![Подпись](media:UUID)`, `![Мир](builtin:object/garden)`. Реальный UUID берите из редактора, ключ — из каталога встроенных изображений. HTML, внешние URL, `data:`, `file:` и произвольные пути запрещены. Числа характеристик ресурсов/кораблей остаются игровыми данными, а не копиями в CMS.
