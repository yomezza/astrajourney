# Astra Journey — Backend: внедрение нового интерфейса «Уведомления» в production

Ты — Backend-разработчик проекта Astra Journey (Cosmosimulator).

**Репозиторий:** https://github.com/yomezza/astrajourney

## 1. Задача

Необходимо перенести в production ранее разработанный и утверждённый frontend-прототип модуля **«Уведомления»**.

Владелец проекта выбрал окончательный вариант оформления:

**A — Compact Chat Style.**

Твоя задача — интегрировать именно этот вариант в существующую игру с сохранением реальной функциональности уведомлений и совместимости с действующими игровыми сервисами.

Это не разработка нового интерфейса с нуля. Frontend-разработчик уже выполнил визуальную и интерактивную часть.

**Не придумывай новый дизайн и не смешивай варианты A, B и C.**

# Часть I. Production-интерфейс

## 5. Компактное окно

Существующее окно уведомлений необходимо привести к размеру и плотности интерфейса чата.

Ориентир начального размера: **примерно 420 × 540 px**.

Это стартовые размеры, а не жёсткое ограничение. Окно должно нормально изменяться в размерах.

### Заголовок

Компактная панель:

**Уведомления · счётчик непрочитанных · управление окном**

Используй существующий оконный менеджер `Modules`.

Не создавай новый менеджер окон, дополнительный диалог или самостоятельную систему сохранения позиции.

Сохрани стандартные возможности:

- перемещение;
- изменение размеров;
- закрытие;
- закрепление;
- управление слоями;
- восстановление расположения.

### Основная область

Список уведомлений должен прокручиваться внутри окна.

Не допускается ситуация, когда прокрутка длинного списка начинает прокручивать главную страницу игры.

Используй `min-height: 0`, правильную flex-компоновку и локальный `overflow-y: auto`.

### Компактные строки

Каждое уведомление показывает:

- тематическую иконку;
- заголовок;
- краткий текст;
- время;
- ненавязчивый индикатор непрочитанного.

Длинные тексты должны сокращаться в обычной ленте.

При открытии уведомления пользователь видит полное содержимое.

Не превращай каждую запись в большую отдельную карточку.

# Часть II. Реальная функциональность

## 7. Существующий API уведомлений

В текущем backend уже реализован маршрут уведомлений.

Исходник:

`internal/notifications/notifications.go`

Получение уведомлений:

`GET /api/notifications`

Ответ содержит:

- `items` — список уведомлений;
- `count` — общее количество;
- `unread` — количество непрочитанных.

Каждый элемент имеет поля, включая:

- `id`;
- `kind`;
- `level`;
- `message`;
- `data`;
- `created_at`;
- `seen`.

### Отметка одного уведомления

Используй существующее действие:

```json
{
  "action": "seen",
  "ids": [123]
}
```

### Отметка всех уведомлений

```json
{
  "action": "seen",
  "ids": []
}
```

Пустой массив для `seen` означает все уведомления текущего пользователя.

### Удаление выбранных

```json
{
  "action": "delete",
  "ids": [123]
}
```

### Очистка всех

```json
{
  "action": "clear"
}
```

**Не создавай новые API для этих операций.**

Backend уже проверяет принадлежность уведомлений пользователю через `user_id`.

Не изменяй эти проверки и не ослабляй авторизацию.

---

## 8. Правильная работа счётчика

Особенно важно исправить отображение счётчика, если текущий frontend использует общее количество уведомлений.

Теперь счётчик должен показывать **количество непрочитанных из `unread`**.

Не путай:

- `count` — все уведомления;
- `unread` — непрочитанные.

После отметки прочитанным, удаления или очистки необходимо получать актуальное серверное состояние.

Не считать данные браузера окончательным источником истины.

Существующий backend возвращает максимум 500 последних записей в `items`. При этом `unread` учитывает все непрочитанные уведомления пользователя.

Учитывай это различие при фильтрации и отображении счётчика.

---

## 9. Режимы просмотра

Реализуй:

**Все** — показывает загруженные уведомления.

**Непрочитанные** — показывает загруженные уведомления с `seen = false`.

При отметке отдельной записи в режиме «Непрочитанные» она должна корректно исчезать из списка после подтверждения операции.

При переключении фильтра не должны теряться другие данные.

Если на сервере непрочитанных больше, чем содержится в последних 500 загруженных записях, не показывай некорректное сообщение о полном отсутствии непрочитанных. Ограничение списка нужно учитывать явно.

---

## 10. Полный текст и действия

Клик по уведомлению открывает его подробности.

Используй реальные поля и существующий `eventText(item)`.

При отображении внешнего текста используй безопасную DOM-вставку через `textContent` и существующие методы UI.

Не вставляй пользовательские сообщения через небезопасный `innerHTML`.

### Сохрани существующие игровые переходы

В текущем модуле есть действия:

- «На карте»;
- «Корабль»;
- «Трюм»;
- «Открыть поверхность»;
- «Открыть проект».

Эти действия должны продолжать работать.

Особое внимание: существующая команда `select_ship` может изменить активный корабль аккаунта.

**Нельзя автоматически выполнять `select_ship` просто при открытии уведомления.**

Переход к кораблю должен оставаться отдельным явным действием пользователя с сохранением действующих игровых проверок.

Также сохрани функции удаления отдельных и выбранных уведомлений и очистки списка. Ради компактности их можно разместить в меню дополнительных действий.

## 11. Категории уведомлений

В прототипе используются пять визуальных групп:

1. Системные.
2. Экономические.
3. Исследовательские.
4. Корпоративные.
5. Игровые.

В production эти группы должны определяться по существующим `kind` и `level`.

Не вводи новые серверные категории только ради оформления.

Ориентировочное соответствие:

| Вид уведомления | Визуальная категория |
|---|---|
| `research_complete` | Исследования |
| `delivery_complete` | Экономика |
| `company_invitation`, `project_complete`, `colony` | Корпорация |
| `arrival`, `landing_ready`, `mining_complete`, `portal_open` | Игровые |
| `message` и неизвестные типы | Системные |

Сохраняй существующую локализацию RU/EN.

Неизвестные типы должны отображаться безопасно и нейтрально.

# Часть III. Архитектура и безопасность

## 12. Что нельзя переносить из демоверсии

Не переносить в production:

- `fixtures.js` как источник данных;
- фиктивные сообщения;
- локальную mock-модель уведомлений как источник истины;
- демонстрационный оконный менеджер;
- переключатели визуальных вариантов;
- тестовые настройки лаборатории;
- код имитации действий.

Используй существующие:

- `createNotifications()`;
- `loadNotifications()`;
- `notificationBadge()`;
- `renderNotifications()`;
- `Session`;
- `Modules`;
- `UI`;
- `I18n`;
- `api()`.

Можно реорганизовать рендеринг и выделить небольшие frontend-компоненты, если это улучшает поддержку кода.

При этом сохрани публичное поведение модуля и его интеграцию с остальной игрой.

## 13. Чат не изменять

Новый интерфейс уведомлений должен визуально соответствовать чату, но не зависеть от его runtime-состояния.

Запрещено:

- создавать второе подключение к Chat Service;
- создавать дополнительный WebSocket;
- дублировать DOM чата;
- менять интерфейс или логику чата ради редизайна уведомлений.

Чат и уведомления должны оставаться двумя самостоятельными модулями одной визуальной системы.

## 14. Состояние сессии

Сохрани проверки `Session.signedIn` и `Session.epoch`.

После выхода пользователя из аккаунта уведомления прежнего пользователя не должны оставаться в интерфейсе другого аккаунта.

Поздние ответы API не должны восстанавливать устаревшие данные после logout.

При выполнении действий:

- блокируй повторные нажатия на время запроса;
- корректно обрабатывай ошибки;
- используй штатные уведомления об ошибках;
- сохраняй фильтр и по возможности позицию прокрутки;
- не удаляй запись из интерфейса окончательно до подтверждения сервером.
