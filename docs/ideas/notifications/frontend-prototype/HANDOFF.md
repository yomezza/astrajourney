# Уведомления Astra Journey — передача backend-разработчику

**Статус:** frontend-only дизайн, не разрешение на production-перенос.  
**Исходник:** `docs/ideas/notifications/frontend-prototype/`.  
**Рекомендуемое оформление:** **A — Compact Chat Style**, потому что его плотность и компоненты ближе всего к чату.

## 1. Что уже готово

Интерактивная демонстрация на самостоятельных `index.html`, `styles.css`, `app.js`, `fixtures.js`. Поддержаны три CSS-варианта, статусы прочтения, счётчик, показ всех/непрочитанных, полнотекстовый просмотр, компактный скролл, mock-сценарии и адаптивность. Всё работает без игрового API, авторизации и WebSocket. Это **визуальная и поведенческая спецификация**, не промышленная реализация.

Не переносить в production файл `fixtures.js`, тестовые кнопки «40 событий» / «Пустой список», модель local-only состояния как источник истины и автономное позиционирование тестового окна.

## 2. Сверка с реальными текущими контрактами

Проверенные исходники в `main` на момент работы:

- `internal/server/web/features/notifications/index.js`: фабрика `createNotifications`, функции `loadNotifications`, `notificationBadge`, `renderNotifications`, создание существующих окон и действий.
- `internal/notifications/notifications.go`: текущая серверная обработка `notifications`.
- `internal/server/web/ui/windows.js`: штатный менеджер окон.
- `internal/server/web/features/chat/index.js` и `scripts/frontend-generation/mock/chat-native.css`: визуальный ориентир.

**Реальный контракт уже содержит поддержку прочитанного!**

- `api("notifications")` → `{items, count, unread}`.
- `items[]` содержит, среди прочего, `id`, `kind`, `level`, `message`, `data`, `created_at`, `seen`.
- `api("notifications", {action:"seen", ids:[id]})` помечает выбранную запись прочитанной, а `{action:"seen", ids:[]}` — все записи пользователя. Сервер применяет ограничение `user_id`.
- `api("notifications", {action:"delete", ids:[...]})` удаляет указанные записи; `{action:"clear"}` очищает inbox. Сохраняйте существующую функциональность: при переносе её можно разместить в контекстном меню, не перегружая строки.
- Сервер возвращает до **500** самых новых уведомлений в `items` (по убыванию `id`). Поле `count` — **общее** количество, `unread` — количество с `seen = false`. Не трактовать `count` как число непрочитанных.

**Не добавлять новые API без необходимости.** Показ `seen`, одинарная и массовая отметка могут использовать существующий контракт после отдельного разрешения на внедрение.

## 3. Соответствие полей и отображения

| Поле прототипа | Реальные данные | Действие при интеграции |
| --- | --- | --- |
| `id` (`mock-n-...`) | `item.id` (числовой) | Использовать только серверный ID; DOM-ID создавать безопасно |
| `read` | `item.seen` | `read = Boolean(item.seen)` |
| `kind` | `item.kind` | Сопоставить с 5 визуальными группами; неизвестное — нейтральный тип |
| `level` | `item.level` | Сохранить серверный уровень, показать деликатный акцент |
| `title` | `item.kind` + доступные данные | Формировать с помощью существующих `I18n.t()` и `eventNames`, не из mock |
| `text` | `message`, `data`, `eventText(item)` | Использовать существующие formatter и экранированный DOM `textContent` |
| `createdAt` | `item.created_at` | Форматировать дату через действующий `fmtTime()` / локаль |
| UI-счётчик | `unread` | Использовать серверное число, не подсчитывать только из первых 500 |

Примерная визуальная классификация (НЕ новые серверные значения `kind`):

- **Исследования:** `research_complete`.
- **Экономика:** `delivery_complete`.
- **Корпорация:** `company_invitation`, `project_complete`, `colony`.
- **Игровые:** `arrival`, `landing_ready`, `mining_complete`, `portal_open`.
- **Системные:** `message` и неизвестные типы (с учётом `level`).

Не менять `kind` на уровне данных: соответствие относится исключительно к CSS и выбору иконки. Проверять новые виды событий по мере расширения игры.

## 4. Как интегрировать после отдельного утверждения

1. Сравнить дизайн A, B, C и утвердить один с владельцем. **До этого production не трогать**.
2. В существующем `createNotifications()` заменить только логику построения DOM и локальные стили отображения; сохранить текущие `loadNotifications`, `notificationBadge`, `Session.epoch`, `I18n`, `Modules` и API-контракт.
3. Монтировать новый список в **существующий** `#window-notifications .module-content`; **не создавать** новый плавающий оконный менеджер или копию чата. В `Modules` остаются штатные titlebar, pin, close, resize и z-index.
4. Перенести стиль из `styles.css` **выборочно**: строки, группы, скролл, футер и badge. Не копировать `.lab-*`, `.preview-*`, `.notice-window` с его автономным `position/resize`, или декоративную сцену.
5. Новые CSS-селекторы должны быть строго scoped, например `#window-notifications .notification-compact-*`. Не переопределять глобальные `header`, `main`, `.module-content` и селекторы чата.
6. Для **отметки прочитанным** применять существующий `action:"seen"`, затем перечитывать авторитетный результат API, сохранять прокрутку и выделение, блокировать повторную отправку при ожидании. Ошибки отображать штатным `notify`.
7. **Полный текст:** использовать existing `eventText(item)` и реальные данные; не генерировать тестовые сообщения. Сохранять логическую навигацию и права на действия.
8. Существующие контекстные действия (карта, планета, колония, корабль, трюм), удаление и очистка должны **остаться доступными**. При открытии `ship` реальная команда `select_ship` может менять активный корабль — не привязывать её автоматически к клику по строке.
9. Придерживаться штатных `I18n` RU/EN, `Session` lifecycle и обработки `signedout`; в UI не должно оставаться данных другого аккаунта.
10. Проверить обновление счётчика после `seen/delete/clear`, список 0/500, длинные строки, поздние ответы API, работу в окне 320–520 px, скролл без прокрутки основной страницы, tooltip, клавиатуру, темизацию и отсутствие влияния на чат.

## 5. Что намеренно не делает прототип

- Не делает `fetch`, `api`, `WebSocket`, запись в PostgreSQL или другой внешний вызов.
- Не копирует исходники Chat Service и не создаёт его второй экземпляр.
- Не авторизует пользователя, не сохраняет события и не изменяет права.
- Не использует абсолютные URL, внешние ассеты, Node/npm для запуска UI.
- Не исправляет production-код уведомлений в рамках этой задачи.

## 6. Перед выпуском

Попросить backend-разработчика показать diff, где видно, что он переносит лишь утверждённый дизайн, проверяет существующие `seen/delete/clear` контракты и сохраняет все навигационные действия. Тесты проводить на отдельной среде. Решение о переносе и слиянии — **только после отдельного разрешения владельца**.
