# Организация репозитория Astra Journey

**Статус:** действующие организационные соглашения с момента публикации.  
**Репозиторий:** `yomezza/cosmosimulator` — **имя репозитория пока не меняем**; название игры — **Astra Journey**.  
**Кому читать:** владельцу, архитектору, backend/frontend/DBA-разработчикам, графическим и SVG-ассистентам, локальным LLM.

Краткий обязательный вводный документ — [AGENTS.md](../AGENTS.md). Этот файл раскрывает практические правила и план дальнейшего упорядочивания. Его публикация **не означает**, что все будущие каталоги и процессы уже внедрены.

## Главный принцип

> **Ветка отвечает на вопрос «над чем сейчас работаем?», а каталог — «что это за материал и кому он предназначен?»**

- Ветки описывают **временную работу**; они не служат вечным складом документации или промптов.
- Каталоги описывают **назначение содержимого** и переживают смену задач и исполнителей.
- `main` — актуальная интеграционная версия проекта. Публикация завершённого изменения в `main` — отдельное, осознанное действие.

## 1. Ветки и ответственность

| Имя | Для чего | Жизненный цикл |
| --- | --- | --- |
| `main` | Актуальный код, утверждённые документы, текущий релизный процесс | Постоянная |
| `docs/<topic>` | Документация, концепция, регламенты | Временная, затем PR в `main` |
| `feature/<topic>` | Новая игровая или интерфейсная возможность | Временная |
| `fix/<topic>` | Исправление ошибки | Временная |
| `experiment/<topic>` | Демонстрация, испытание идеи, прототип | Временная; необязательно вливать в `main` |
| `chore/<topic>` | Инструменты, реорганизация, обслуживание | Временная |

Примеры: `docs/pilot-terminal-architecture`, `experiment/pilot-terminal-tabs`, `feature/planet-colony-catalog`.

**Не используем** в качестве основного рабочего процесса постоянные `documentation`, `prompts`, `frontend`, `backend` или отдельные ветки для каждого чата: они быстро разойдутся с `main`.

Стандартный порядок: проверить актуальный `main` → создать ветку под конкретную задачу → выполнить только согласованные изменения → запустить релевантные проверки → оформить PR с описанием → слить после разрешения/проверки → закрыть временную ветку. Если владелец явно разрешил прямой коммит в `main`, это допустимое исключение.

Разным чатам лучше назначать **непересекающиеся области файлов**. Если необходим общий файл, согласовать порядок правок или объединять изменения через PR; не делать force push в чужую работу. Коммиты и ссылки на них — общая память проекта, а не заявления на словах.

## 2. Назначение каталогов

| Каталог | Что в нём хранится |
| --- | --- |
| `cmd/` | Точки запуска Go-программ |
| `internal/` | Go-логика, сервисы, рабочий браузерный клиент |
| `configs/` | Примеры конфигурации и связанные файлы |
| `tests/` | Автоматизированные тесты |
| `scripts/` | Сборка, генераторы, инструменты и изолированная frontend-демосреда |
| `docs/ideas/` | Предлагаемые механики, UX-концепции, исследования |
| `docs/design/` | Визуальные эталоны, исходники, требования к графике |
| `docs/operations/` | Развёртывание, эксплуатация, процедуры |
| `docs/roadmap/` | Согласованные планы с проверяемым статусом |
| `docs/archive/` | История; не обязательно применима к текущему коду |
| `release-notes/` | История выпущенных версий |
| `downloads/` | Релизные бинарники и контрольные суммы **в нынешней схеме** |
| `.github/workflows/` | Реально исполняемые GitHub Actions |
| [`ai/`](../ai/README.md) | Промпты, handoff-материалы и шаблоны для разных ИИ |

Существующие специализированные каталоги (например, `docs/chat-service/`, `docs/planetary/`, `docs/refactoring/`, `docs/audits/`) **не переименовываем автоматически**. Их перенос требует проверки входящих ссылок и актуальности.

**Одна идея — один главный документ.** Для «Командного терминала пилота» исходная концепция живёт в `docs/ideas/pilot-command-terminal/`; [задания для архитектора и frontend](../ai/prompts/README.md) должны **ссылаться** на неё, а не копировать её с противоречащими правками.

### Как различать статус материалов

- `idea / draft` — предложение, не подтверждение игровой механики.
- `review` — ожидает технической/продуктовой проверки.
- `approved` — решение одобрено, но не обязательно написан код.
- `implemented` — наличие реализации **проверено в актуальной ветке**, с указанием файлов и версии.

Статус конкретной идеи следует фиксировать в её `README.md` или `README.ru.md`. Не проставляй `implemented` по одному промпту, макету, обещанию ИИ или старому релизу.

Навигатор [docs/README.md](README.md) и реестр [docs/ideas/README.md](ideas/README.md) опубликованы. Статусы идей отражают границы документов и не подменяют проверку работающего кода.

## 3. Промпты для нескольких чатов — действующая структура

В `main` после слияния [каталог `ai/`](../ai/README.md) хранит задания **по ролям**:

```text
ai/
  README.md
  prompts/
    README.md
    architecture/001-pilot-command-terminal/prompt.md
    frontend/001-pilot-command-terminal/prompt.md
    backend/README.md
    dba/README.md
    graphics/README.md
    svg/README.md
  handoffs/README.md
  templates/prompt.md
  templates/handoff.md
```

- **Роль задаёт каталог**, а не имя Git-ветки. Номер `NNN` последовательно назначается **внутри роли**.
- Нумерация запущена в новом `ai/`, она **не** переименовывает историю прежних чатов и документы с `01`, `02` в `docs/ideas/`.
- Одна концепция может получать разные задания для архитектора, frontend, backend и DBA. Исходная идея остаётся в `docs/ideas/`, промпты только ссылаются на неё.
- `prompt.md` — постановка задачи, **не доказательство выполнения и не разрешение её начинать**. В `handoffs/` записываются только проверенные итоги и реальные ссылки на коммиты.
- Пример `architecture/001-pilot-command-terminal` архивирует уже выполненную постановку, а `frontend/001-pilot-command-terminal` подготовлен для следующего **отдельного** поручения владельца.
- Новые чаты должны прочитать `AGENTS.md`, документацию из реестра и актуальный код; выдуманные API, статусы и результаты тестов запрещены.

Старые материалы переносить только по отдельному согласованному плану с сохранением ссылок.

## 4. Безопасность при работе ИИ-разработчиков

1. Прочитать [AGENTS.md](../AGENTS.md), корневой README, документацию задачи и относящиеся к ней реальные исходники.
2. Убедиться, что ветка/контекст/версия относятся к текущему запросу; проверить, не исправляет ли соседний чат те же файлы.
3. Не превращать идею в production-изменение без отдельной команды. Для изолированных frontend-экспериментов использовать `scripts/frontend-generation/` с mock-данными.
4. Не запускать операции над рабочей PostgreSQL, миграции, изменение прав, удаление данных или секретов без отдельного разрешения и плана отката.
5. Не подменять существующие технологии новыми библиотеками, backend-службами и сложной инфраструктурой ради простого UX-эксперимента.
6. Сохранять существующие игровые API, права доступа и релизные требования. При сомнении сначала исследовать и описать ограничения.
7. Разделять **изменения на диске**, **коммит в GitHub**, **слитый PR**, **успешные тесты** и **выпущенный релиз** — это разные состояния работы.

## 5. Как завершать задачу и передавать следующему чату

Минимальный проверяемый отчёт:

```text
ЗАДАЧА: ...
СТАТУС: выполнено / частично / только исследовано
ВЕТКА: ...
КОММИТ: ... (если реально создан)
PR: ... (если реально создан)
ИЗМЕНЕНО: пути файлов
ПРОВЕРЕНО: конкретные проверки и их результаты
НЕ ПРОВЕРЕНО: ...
РИСКИ / НЕЗАКРЫТЫЕ ВОПРОСЫ: ...
СЛЕДУЮЩИЙ ШАГ: ...
```

Ссылки на собственные коммиты и актуальные источники важнее длинного рассказа. Нельзя заявлять, что задача выполнена, если есть лишь промпт для другого исполнителя.

## 6. Бинарники и история релизов — ничего не удалять пока

В текущем репозитории `scripts/build-release.py` записывает бинарники в `downloads/`; `.github/workflows/release.yml` при тегах `v*` проверяет `downloads/SHA256SUMS` и публикует файлы в GitHub Releases.

**Следствие:** просто удалить исторические EXE или переместить `downloads/` — значит рискнуть существующим релизным конвейером. Позже отдельно спроектировать переход на сборку артефактов в CI и хранение их в GitHub Releases; отдельно учесть старые ссылки, контрольные суммы, обратную совместимость и размер Git-истории.

Первый этап организации не меняет ни одной сборки, тега, workflow, Git-истории или исполняемого файла.

## 7. Этапы уборки

1. **Правила — завершено:** корневой `AGENTS.md`, этот документ, ссылка из `README.md`.
2. **Навигация — создана:** `docs/README.md`, `docs/ideas/README.md`; более глубокая ревизия старых материалов остаётся отдельной задачей.
3. **Работа ИИ — структура создана:** `ai/` с промптами, ролевым реестром, handoff и шаблонами. Исторические материалы **ещё не переносили**.
4. **Релизные артефакты — не начато:** отдельно согласовать пересмотр сборок и `downloads/` без нарушения текущих публикаций.

**Критерий хорошего порядка:** новому ИИ-разработчику достаточно открыть `AGENTS.md`, перейти по ссылке к своей задаче и за несколько минут понять, где истина, где черновик и где можно безопасно работать.
