# Правила разработки и handoff

## Аудит существующей реализации (main 60f2fcd...)
- web/features/studio/index.js: types собирается из labels/dashboard; каталог блокирует второй экземпляр по type; paintWindow и moduleAction используют focusShipID (workspace ship либо active ship); для старых окон возможен select_ship после подтверждения. view=card/window — размещение, не функциональный подвид.
- web/features/studio/views.js, dashboard.js: семь типов fleet, overview, operations, map, market, mining, cargo. fleet/overview — сводки корабля; map — сводка маршрута; market локальные цены зависят от активного корабля. Не объявлять весь текущий Studio бесполезным.
- internal/workspaces/layout.go, service.go: v1, лимиты 10/16/64 KiB, UUID, JSONB revision, права на новые ship bindings, существующие устаревшие связи допускаются для объяснения. Сохранить гарантии.
- internal/navigation/commands.go: route/explore до 20 точек, расчёт пути, топлива, времени, проверка доступности/idle, cancel_route очищает оставшиеся waypoints и reserved_fuel, а не обещает мгновенную остановку. rescue — платный серверный сценарий; portal_travel — существующая команда. Не менять правила без задачи.
- internal/fleet/{model,modules,operations,position,ships}.go, web/features/fleet/index.js, web/features/maps/galaxy.js, web/features/navigation/pickers.js — повторно изучить фактические контракты. Не считать, что все сценарии уже имеют независимый API.

## Этапы
1. Сверить актуальный main, AGENTS.md, docs/README.md, ai/README.md, текущие PR и спецификацию. Зафиксировать baseline SHA и отличия.
2. Backend — аудит API/permissions, согласованный контракт, совместимое серверное хранение и migration, адресные операции. Опубликовать DTO/ошибки/примеры/fixtures/версию в своей ветке; Frontend может параллельно готовить архитектуру и mock-прототип, но не выдумывать production API.
3. Frontend — реестр, экземпляры, два контейнера, resolver, каталог, compact shell, M001.01, M002.01–03, M003.01–02. Подключать только проверенные контракты.
4. Совместная проверка в тестовой среде. Не merge/deploy/release без владельца; не применять SQL к production. Отдельные feature-ветки от свежего main, не эта docs-ветка. Не конфликтовать с другими задачами. Согласовать порядок интеграции Backend → Frontend; если спецификация ещё не в main, читать её по ветке/commit и не затягивать несвязанные изменения.

## Миграция
Предложить детерминированное отображение fleet/overview → ship.owned (не потерять UUID/геометрию и осознанно обработать дубли), cargo → inventory.cargo, map → navigation.interstellar только когда эквивалентен сводке маршрута; остальные типы сохранять совместимым legacy adapter до их паспортов. Не удалять данные раскладок или недоступные объекты, не менять привязки молча. Обработать ship_id=0 (раньше active fallback): явный выбор или безопасное согласованное начальное назначение, не выбирать случайную цель. Не смешивать новый permanent layout с временными окнами; судьбу старого view=window описать отдельно. Проверить новую и существующую тестовую БД, совместимость старого Web при rollout, откат/backup. Конкретная миграция — предложение, до реализации уточнить и согласовать; не навязывать схему.

## Общие критерии
Два пространства с A/B и два экземпляра в одном с A/B; одинаковые имена кораблей, но IDs различны. Команды на A не влияют на B и active ship. Пространство без корабля, fixed binding, derived без стыковки, потеря прав, конфликт ревизии, UUID другого аккаунта, logout/login, F5 и смена устройства. Плавающий инструмент остаётся на A после перехода к B. Лимиты и адаптивность (320px и desktop), клавиатура, RU I18n. Чат/уведомления в старом стиле и с прежними функциями; Planet Mode, старые окна, существующие игровые операции без регрессий. Проверить нагрузки, отсутствие запросов на каждый модуль/кадр и утечек listeners. Отчёт: файлы, ветка, SHA, PR, фактические тесты и не выполненные, ограничения, миграция/rollback, дальнейшие шаги.

## Не входит в задачу
Межмодульные взаимодействия и DnD между экземплярами, будущие подвиды/семейства, Economy service, смена правил экономики, redesign Chat/Notifications, новые игровые механики, выкладка. Не добавлять обязательные зависимости/службы без разрешения. Если существующая игровая механика не поддерживает утверждённый сценарий, указать gap и предложить минимальный контракт, не имитировать успешную операцию.
