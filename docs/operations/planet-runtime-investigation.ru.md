# Расследование зависаний Planet после 0.25.0

## Статус и границы доказательств

Основа работы — `main`, `aa55aa9d3aa0d0274602c15bae59faa0d25108ce`
(0.25.7). Сверено через `git ls-remote origin refs/heads/main`.
Изменения подготовлены в `fix/planet-runtime-investigation`.
По журналам локального Windows-запуска установлен источник регулярных рывков:
полное чтение JSON мира внутри `Navigation.AdvancePlayer`, удерживающего общую
exclusive-блокировку Cosmos. Проверка Planet синхронно ждёт shared-блокировку,
а её WS-обработчик в это время не отправляет очередные кадры движения.

Это подтверждённый механизм задержек в присланном инциденте. Старые постоянные
переподключения на другой установке этим журналом не воспроизведены: в нём одно
соединение с одной epoch, завершённое остановкой службы. Тайм-ауты и политика
повторных подключений не менялись.

## Доказательства из присланного инцидента и исправление

* Мир содержит 14 500 систем. В журнале Cosmos fingerprint
  `a180058bf3b3f048` соответствует `SELECT data FROM galaxies WHERE name='Edem'`.
  17 вызовов в фазе `advance_player` занимали 523 мс по медиане, до 702 мс.
* За 75 секунд одного активного посещения 12 проверок Planet заняли больше
  500 мс, максимальная — 821 мс. Сопоставленные shared world lock ожидали
  Cosmos; замеров ожидания свободного соединения пула нет, пул не насыщен.
* Например, 11:29:47 Cosmos читал JSON 526 мс и закончил advancement за 929 мс.
  В этот же момент Planet ждал shared world lock 739 мс. Все времена — +05:00.
* В 11:30:54 закрытие зафиксировано как `service_shutdown`, следом `service stopped`.
  Две неудачные попытки подключения через Cosmos идут уже после остановки Planet.
  Ошибки Chat соответствуют незапущенной службе. Первые auth-запросы предшествуют
  входу; последующего сброса сессии внутри активного посещения не зафиксировано.
* CSP-ошибка запрещённого inline-скрипта не содержит источника/stack. У страницы
  внешний module entry; оснований ослаблять CSP или связывать эту ошибку с
  SQL-задержками нет.

Причинное изменение в `0f4accd`: `AdvancePlayer` начал вызывать
`World.LoadFrom(ctx, tx)` вместо кэшированного `World.Load(ctx)`. Транзакционный
`LoadFrom` намеренно возвращает отдельную изменяемую копию и поэтому каждый раз
читает/разбирает полный мир. Такой путь нужен писателям, но был поставлен на
обычный периодический advancement. Опрос Cosmos продолжается и в PlanetMode.

Добавлен отдельный `World.LoadReadOnly`: проверка видимой версии строки через
`xmin::text` на том же соединении, затем повторное использование неизменяемого
кэша при совпадении. Проверка не передаёт и не разбирает большой JSON. При
изменении версии читается актуальный snapshot; транзакционные снимки не
публикуются в общий кэш. Исходный `LoadFrom(tx)` оставлен для писателей,
переименования/rollback не могут изменить общий объект до commit. Обычный кэш
также проверяет версию строки вместо извлечения revision из большого JSONB.
Новые столбцы, миграции и изменение production-БД не требуются.

Regression `TestNavigationPollingDoesNotFetchWholeWorld` на реальной PostgreSQL:
старый navigation-путь — 5 полных чтений за 649,6 мс, тест падает;
исправленный — 0 полных чтений за 11,1 мс, тест проходит. Это локальные замеры,
не обещание конкретной задержки на компьютере владельца. Проверены cold cache
с единственным занятым соединением, изоляция private writer, rollback,
видимость внешнего commit и старого repeatable-read snapshot, а также race.
Проверки переименований, сканирования и разрешённого возврата проходят.

## Сравнение v0.24.17 → v0.25.0

Сравнивались полученные из origin теги, а не описания релизов.
Основная реализация — `0f4accd` (слияние `82c261a`):

| Область | Реальное изменение | Значение для расследования |
| --- | --- | --- |
| `features/planet/mode.js`, `visit.js` | Новый отдельный host, inert/скрытие космического UI, Startup overlay, восстановление после загрузки страницы | PlanetMode не уничтожает приложение Cosmos. Основной HTTP polling и транспорт Chat продолжают работать. |
| `visits/return.go`, `transfer/proof.go`, schema 253 | `leave` заменён на `return.prepare` и серверное разрешение возврата; схема Planet 7 → 8 | Проверять подготовку возврата и идентичность посещения/эпохи. Само движение не вызывает подготовку возврата. |
| `visits/lifecycle.go` | Истёкшая сессия переводит посещение в disconnected вместо ended | При валидной сессии эта ветка не выполняется. Нужен факт отказа проверки сессии, а не предположение о нём. |
| `visit.js` / `transfer/service.go` | Обновление названий/состояния посещения через Cosmos примерно раз в 15 секунд, дополнительные read-only joins | Этот запрос запускает reconcile и конкурирует за общий world lock. Старый обработчик закрытия ограждён текущим socket/task. |
| `navigation/advancement.go` | `World.Load` заменён на `World.LoadFrom(ctx, tx)` под exclusive world lock | Подтверждённая регрессия: read-only advancement перестал использовать кэш и регулярно читает весь JSON мира. |
| `worldstore/repository.go` | Кэш мира стал перепроверять `data->>'revision'` спустя две секунды; загрузка/проверка может выполняться внутри `AdvancePlayer`, удерживающего exclusive advisory lock 784218 | Возможный вклад в задержки. На локальном мире из 3000 систем проверка ревизии заняла 7,5 мс; этого недостаточно, чтобы объяснить постоянные тайм-ауты. Причина не доказана. |
| `knowledge/media.go`, `server/run.go` | Новый worker обслуживания медиа: при старте, затем раз в час | Не совпадает с непрерывными переподключениями сам по себе. |

Heartbeat с проверкой посещения раз в секунду, checkpoint примерно раз в пять
секунд и shared world lock Planet уже были в 0.24.17. Версии pgx и coder/websocket
между этими тегами не изменились. Их нельзя объявлять новой регрессией без
дополнительных доказательств. Исправления 0.25.1–0.25.7 сохранены.

## Что записывается

В общий TOML добавлен необязательный раздел:

```toml
[diagnostics]
directory = '/var/lib/astra-journey/diagnostics'
enabled = true
```

Каждая служба пишет `cosmos.jsonl`, `planet.jsonl` или `chat.jsonl`, одновременно
выводя журнал в stderr. Существующий `planet.log_file` поддерживается и получает
те же записи. При отсутствии directory остаётся stderr. В начале есть запись
`diagnostics started`, PID и Git revision/modified сборки. Каталог должен быть
доступен для записи всем используемым служебным аккаунтам; для разных аккаунтов
его нужно заранее подготовить с общей группой. Ошибка открытия не замалчивается.
В TOML-режиме переменные окружения приложения не подмешиваются; настройки
нужно добавлять именно в выбранный `CONFIG_FILE`.

* `X-Request-ID`: браузерный HTTP-запрос → Cosmos → Planet/Chat.
  Для WebSocket браузер передаёт случайный UUID `request_id` в query, шлюз
  переносит его в заголовок. Это идентификатор диагностики, не авторизация.
* `visit_id`, `user_id`, `connection_epoch`, fence: активация, проверки,
  сохранение, старый disconnect, переход в сектор. Старый disconnect пишет
  `applied=false`, если его epoch уже заменена.
* Закрытие Planet WS: этап, продолжительность, сторона (`planet`, `peer` или
  `transport_or_peer`), полученный close code. Для EOF/1006 физический инициатор
  остаётся неизвестным. Серверный `CloseNow` не выдаётся за graceful close.
* Chat: создание/завершение соединения, lease generation, отказ проверки
  сессии/аренды/области, ошибки записи. Текст сообщений не записывается.
* БД: время ожидания пула от 50 мс, длительность SQL от 250 мс и ошибки,
  SQLSTATE, PID backend, начало/commit транзакций, безопасный hash SQL и этап.
  Текст SQL и его параметры не записываются. Сам текст ошибок PostgreSQL
  также не выводится: он может содержать значения параметров.
* Раз в секунду отдельное диагностическое соединение (максимум одно на службу)
  снимает до 32 ожиданий SQL-lock и `pg_blocking_pids`. Раз в пять секунд
  выводится состояние основного пула. Если прав/подключения недостаточно,
  появляется `db observer unavailable`; отсутствие записей не доказывает
  отсутствие блокировок. Наблюдение не использует слоты основного пула.

`enabled=false` отключает подробный SQL/HTTP tracing и наблюдатель БД.
Файлы не ротируются приложением; используйте штатную ротацию/ограниченный
период сбора. Никакие новые права БД или секреты автоматически не назначаются.

В браузере есть кольцевой буфер последних 400 диагностических событий:
PlanetMode enter/leave, создание socket, welcome, готовность сцены, серверный
отказ, закрытие в том числе устаревшего socket, очистка renderer/таймеров,
состояние сессии и транспорта Chat. В DevTools **до перезагрузки страницы**:

```js
copy(JSON.stringify((await import('/core/diagnostics.js')).events(), null, 2))
```

Буфер хранится только в памяти вкладки. Поля ограничены allowlist; пароли,
cookies, токены, билеты высадки, DSN, тела HTTP/WS и сообщения Chat не собираются.
Диагностика браузера не отправляется отдельным фоновым запросом на сервер.

## Проверки

На изолированной PostgreSQL 17, Go 1.26.11 и Chromium:

* `TestPlanetModeWithCosmicWorkers` — 70 секунд реальных кликов/движения,
  фоновые процессы Cosmos (simulation, landing, reconcile, cleanup, knowledge),
  без искусственной задержки БД: одна WS connection/epoch, движение продолжается.
* `TestDiscoveryGuidePlanetBrowser250` — настоящий PlanetMode, F5 с тем же
  посещением, сохранение геометрии Cosmos, возврат с серверным разрешением:
  пройдено, JS-ошибок нет.
* `TestPlanetDiagnosticsDistinguishesPoolWaitAndSQLLock` — отдельно зафиксированы
  150 мс ожидания пула и 2200 мс SQL-lock, ожидающий PID, blocker PID,
  request/visit/epoch и безопасный SQL hash. Это проверка диагностического
  инструмента, **не воспроизведение причины сбоя владельца**.
* `TestPlanetReturnProof253`, `TestCheckpointCommitFailureIsNotRetryable257` —
  пройдены; контракт возврата и неопределённого commit сохранён.
* Unit-тесты telemetry, configuration, planetserver; проверка защиты логов от
  утечки SQL/параметров/ошибок; UI module architecture и профильный `go vet` —
  пройдены.
* Три реальные Linux amd64 службы отдельно запущены с одним общим TOML;
  регистрация, браузер и WebSocket через Cosmos, записи всех трёх файлов и
  сохранение request ID проверены.

Полный нерелевантный набор тестов и нагрузочное испытание не запускались.
Диагностические сборки сохраняют исходные номера служб main; это не новый
опубликованный релиз и не доказательство устранения исходного дефекта.

## Подтверждение на установке владельца

После замены сборки на установке владельца и повторного воспроизведения нужны три JSONL-журнала за
30 секунд до зависания и до завершения переподключения, а также браузерный
буфер той же вкладки. Достаточно сохранить один инцидент. Нужны также версия
PostgreSQL и наличие/тип внешнего reverse proxy, без конфигурационных секретов.

Сначала связать `planet_server_error` / `planet_ws_close` с request ID в
`planet websocket ended` и конкретным этапом. Затем различить SQLSTATE,
`db acquire` и SQL lock wait, сопоставив backend/blocker PID с транзакциями
Cosmos/Planet/Chat. При 1006 без серверного завершения проверить журнал
внешнего proxy и остановки процесса. Только после этого выбирать исправление
источника; локальные зелёные тесты не заменяют этот журнал.
