# Диагностика загрузки «Галактик» в 0.30.0

## Статус и область

Исследование выполнено по вопросу владельца о медленном открытии раздела и необходимости индексов. Рабочая ветка — `docs/galaxy-admin-performance`, исходный commit `468d533cc68eee228d3aa72d9a88b4791450b612`. Игровой код, миграции, опубликованные сборки и production не изменялись; выполнены чтение исходников и измерение на локальной PostgreSQL в отдельной временной схеме базы `astra_release_test`.

## Подтверждённые причины лишней работы

1. `web/features/workspace/index.js`: каждый зарегистрированный renderer сначала вызывает `ensureMap()`. При пустом `world.data` ожидает `loadWorld()` → `GET /api/galaxy`, то есть весь публичный каталог систем и коридоров. Только затем вызывается `GalaxyAdmin.render()` и `GET /api/admin/galaxies`. Для начального каталога галактик вся карта не требуется; она нужна отдельным действиям предпросмотра. Эта предварительная загрузка выполняется один раз, пока карта не загружена в текущей сессии. Искусственной минимальной задержки в `module-loading.js` нет.
2. `internal/worldstore/galaxy_management.go`, `AdminGalaxies`: GET использует `universestore.Load(ctx, tx)` и повторно читает системы, планеты, природные поля, коридоры, регионы и метаданные. Прогретый неизменяемый кеш `worldstore.Service` этим путём не используется. Для read-only пути уже существует проверяемый по `storage_version` метод `LoadReadOnly`; ветки preview/apply должны сохранять собственную изменяемую копию мира.
3. `galaxyStatistics` вызывается для каждой неудалённой записи каталога. Каждый вызов `plannedPorts` снова обходит весь мир и вызывает `universe.SystemSites`, даже при подсчёте закрытой галактики без систем. Затем ресурсы выбранной галактики снова считаются через `SystemSites`. Внутри строятся объекты, коллекции и детерминированные RNG для астероидного/ледяного поля. Это вычисления Go, а не поиск строк индексом PostgreSQL.
4. `web/features/administration/galaxies/index.js`: выбор другой карточки и переход к черновику повторно вызывают весь `render` с новым запросом каталога. Уже полученные данные не используются для простого переключения редактора.

## Измерение

Стенд: Go 1.26.0, PostgreSQL 17.12 на том же хосте; штатный тестовый мир, 3000 систем, 14946 планет и 84 станции. Восемь последовательных запросов прошли через настоящий HTTP handler с авторизацией администратора; общий кеш мира был предварительно прогрет.

| Показатель | Результат |
| --- | --- |
| `GET /api/admin/galaxies`, 8 запросов | 270,7–317,8 мс, медиана 285,5 мс |
| Размер JSON-ответа | 3724 байта |
| Чтения всех `star_systems` и `system_planets` | по одному на каждый запрос, несмотря на прогретый кеш |
| `SystemSites`, накопленная доля CPU-профиля | около 60,8% |
| `galaxyStatistics`, накопленная доля CPU-профиля | около 61,5% |
| `protectedPorts`, EXPLAIN ANALYZE | исполнение 0,433 мс, планирование 1,989 мс |

Накопленные доли вложенных функций перекрываются и не складываются. Pgx trace включает чтение и декодирование строк Go, поэтому его длительности не выдаются за чистое время исполнения SQL. Восемь вызовов чтения планет суммарно заняли около 335 мс, систем — около 204 мс; это подтверждает дополнительную стоимость полной материализации мира.

Это результаты небольшого локального мира с одной пользовательской записью и почти пустыми таблицами задач/рынка. Они не измеряют сервер владельца, сетевую задержку, большую вселенную, конкуренцию с игровым тиком или SQL на реальных объёмах. Причина конкретной многосекундной задержки владельца без замера его запросов целиком не установлена.

Одноразовый диагностический Go-тест прошёл (`TestGalaxyAdminProfileTemporary`); временный файл удалён из репозитория. В текущей среде сохранены `/tmp/astra-galaxy-admin-profile-test.go`, `/tmp/astra-galaxy-admin-profile.log`, `/tmp/astra-galaxy-admin-cpu.pprof` и `/tmp/astra-galaxy-admin-protected-ports-plan.json`. Профиль снимался только во время восьми HTTP-запросов, после создания и прогрева стенда. Временная схема убрана штатным cleanup fixture.

## Индексы

У систем и планет уже есть PK, UUID, `(system_id, ordinal)`, активный номер и регион галактики. Чтение всех строк с последующим декодированием и пересчётом ресурсов не исчезнет после добавления ещё одного индекса.

В `protectedPorts` есть коррелированные проверки кораблей, складов, бронирований, предложений, задач и доставок. На больших объёмах это отдельный потенциальный источник задержек: существующие индексы часто начинаются с `user_id`, `company_id` или `ship_id`, а проверка ищет по расположению станции. Кандидаты для последующего измерения — частичные индексы расположения активных задач/доставок и `(star, station)` для непустых складов/открытых обязательств. Их добавление пока не обосновано планом на реальных объёмах. В измеренном плане PostgreSQL выгодно читает маленькие таблицы последовательно; наличие Seq Scan само по себе не является дефектом. DDL не выполнялся.

## Рекомендуемое точечное исправление

1. Убрать зависимость первоначального каталога от загрузки всей карты; обязательные для конкретного действия данные загружать перед этим действием. Сохранить общий контракт загрузчика модулей.
2. Для GET переиспользовать проверяемый снимок мира, сохраняя свежие проверки имущества и обязательств станций. Не делить изменяемые снимки preview/apply с read-only кешем.
3. Считать статическую статистику по ревизии мира, одним проходом по системам/коридорам, без повторного построения ресурсов ради подсчёта портов. Динамические защищённые станции учитывать отдельно, чтобы новые склады/задания не делали ответ устаревшим.
4. Переключать редактор по уже полученному каталогу; обновлять после применения/удаления и при необходимости сверять ревизию. Сохранить проверки роли, сессии, отбрасывание старых ответов и черновики формы.
5. Измерить тот же API и начальное открытие в настоящем браузере до/после. Индексы добавлять только для запросов, которые останутся медленными по EXPLAIN ANALYZE на репрезентативных объёмах.

Реализация этих оптимизаций и новый релиз в этот этап диагностики не входят.
