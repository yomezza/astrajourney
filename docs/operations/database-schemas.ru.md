# Разделение PostgreSQL по схемам · 0.27.0

Статус: реализовано в startup-миграции Cosmic. Planet и Chat используют готовую
структуру; самостоятельно таблицы и схемы не создают.

**Перед запуском нового Cosmic менять `search_path` в свойствах БД не нужно.**
Все три службы устанавливают одинаковый путь для каждого физического соединения
пула. Он переопределяет путь из DSN/настроек БД и не содержит `$user` или
посторонних схем. `public` входит только если это прежнее имя установки.

Сохраните прежние БД и `database.schema` в общем TOML. Для `schema = "game"`
корневая схема остаётся `game`, а таблицы размещаются в `game_*`. Это отделяет
несколько установок в одной БД. Не указывайте список схем в `database.schema`:
это по-прежнему **одно имя установки**, а не строка `search_path`.

## Размещение

Разделение по предметным областям: границы служб сохраняются, общая география
и колонизация принадлежат Cosmic, локальные сцены и движение — Planet.
`integration` содержит узкие межсервисные контракты.

| Схема при корне `game` | Содержимое |
| --- | --- |
| `game_identity` | Пользователи, сессии, игровые уведомления, репутация |
| `game_universe` | Каталог галактик, реестр UUID систем, системы, планеты, коридоры, регионы, портал |
| `game_fleet` | Корабли, станции, навигационные заметки, автоматизация и логистика |
| `game_economy` | Рынки, месторождения, добыча, квоты, резервы, финансовый журнал, склады, заказы, доставки, верфи |
| `game_corporations` | Корпорации, роли, заявки, финансы, проекты, взносы, хранилища |
| `game_colonies` | География поверхностей, секторы, колонизация, территории, площадки, названия колоний |
| `game_planet` | Аренда процесса, сохранённые сцены, персонажи, визиты, переходы, постройки, диагностика восстановления |
| `game_chat` | Все таблицы `chat_*`, секции сообщений, последовательности и коллация Chat; исключение — интеграционные функции |
| `game_knowledge` | Исследования, открытия, история имён, база знаний, публикации и медиа |
| `game_integration` | Передача управления, handoff, узкое представление сессий Planet, разрешения возврата, защищённые функции Chat |
| `game_ops` | Время мира, настройки, события, административный журнал, замеры, предложения игроков, версия схемы Planet |
| `game_archive` | Прежняя `galaxies.data`, если она существовала до табличного переноса |
| `game` | `_astra_schema_layout`, представление архивной `galaxies`; пользовательские/extension-объекты, не принадлежащие игре, остаются на месте |

Полная маршрутизация имён — `internal/platform/dblayout/layout.go`; создание
объектов из исторических SQL-миграций направляется туда же. Для длинного имени
или имени вне `[a-z][a-z0-9_]{0,29}` используется стабильный префикс
`aj_<24 шестнадцатеричных символа SHA-256>`. Фактические имена показывает проверка.

Рабочий путь: корень, затем перечисленные области, **без archive**. Функции
получают фиксированный путь с `pg_catalog` первым и `pg_temp` последним;
защищённые функции Chat дополнительно квалифицируют таблицы схемой. Исторический
JSON доступен через корневое представление, его запись блокирует существующий
триггер табличного хранилища.

## До обновления

1. Сделайте согласованный backup БД и файлов данных. Сохраните журнал удалений
   Chat и TOML. **После переноса backup одной `game` недостаточен:** используйте
   полный backup БД либо явно включайте корень и все его доменные схемы, секции
   и зависимости. Не удаляйте прежнюю копию до проверки восстановления.
2. Остановите старые Cosmic, Planet и Chat. Новые и старые процессы одновременно
   запускать нельзя: старые сборки рассчитаны на единственную схему.
3. Замените три сборки на 0.27.0, сохранив прежнее имя установки и пути к файлам.
4. Выполните новым Cosmic проверку с прежним TOML:

Linux:

```bash
CONFIG_FILE=/etc/astra-journey/shared.toml ./astra-journey-v0.27.0-linux-amd64 --check-schemas
```

Windows PowerShell:

```powershell
$env:CONFIG_FILE = 'C:\AstraJourney\shared.toml'
.\astra-journey-v0.27.0-windows-amd64.exe --check-schemas
```

Команда открывает транзакцию READ ONLY. Выводит имена схем, количество отношений,
версию раскладки и `issues`; не запускает HTTP, тики и миграции. Секреты, строки
подключения, токены и игровые строки в отчёт не входят. До переноса
`layout_version: 0`, после — `1`. `ready: true` подтверждает проверенные права
CREATE и отсутствие занятого чужого пространства. Это не замена проверке
владения объектами, доступности расширений и финальной транзакционной миграции.

## Права и фактический перенос

Cosmic выполняет перенос в общей транзакции startup runner под прежними
migration/world advisory locks. Нужны CREATE на БД для отсутствующих схем,
USAGE/CREATE на существующих целевых схемах и права владельца переносимых таблиц,
функций и коллации. Для функций, принадлежащих `chat_definer`, миграционная роль
должна иметь прежнее право их изменять. Наличие только CREATE SCHEMA не заменяет
владение существующими объектами.

Схемы создаются автоматически. `ALTER … SET SCHEMA` сохраняет строки, ID/UUID,
OID, FK, индексы, owned sequences, владельцев и табличные/колоночные ACL. Секции
систем переносятся вместе с родителем и остаются LIST-секциями по `galaxy_id`.
Новые галактики автоматически создают секции в `game_universe`, новые секции
сообщений — в `game_chat`, независимо от первого элемента пути.

Роли, уже имевшие USAGE на корне, получают USAGE на доменные схемы. CREATE
runtime-ролям не добавляется. Существующие права на таблицы и функции сохраняются.
Для вновь созданной отдельной роли нужны USAGE на используемые схемы и прежние
предметные права; `search_path` сам по себе доступа не выдаёт. Команда Chat
`--grant-runtime` поддерживает новую раскладку и сохраняет отдельную NOLOGIN-роль
владельца защищённых функций. Обслуживание секций Chat остаётся отдельной DBA-командой.

Если новая целевая схема уже занята до первой миграции, перенос останавливается;
чужие объекты не присваиваются. Любая ошибка откатывает и перемещения, и создание
схем. После успешного COMMIT корень хранит маркер версии 1; повторный запуск
не создаёт копии игровых таблиц в прежней схеме. Настройки DATABASE/ROLE не меняются.

Запустите **Cosmic первым**, дождитесь `Cosmic initialization complete`, затем
Planet и, если используется, Chat. У всех должны совпадать БД и `database.schema`.
Планетарная версия структуры остаётся 10, Chat — 1, формат табличного мира — 1;
версия раскладки схем хранится отдельно. Внешние SQL-скрипты с жёстким `game.users`
нужно перевести на новые имена или явно задавать опубликованный путь соединения.
Не выполняйте обратный перенос вручную: откат версии — восстановление
согласованного backup и соответствующих ему файлов/журнала.

## Проверка реализации

На изолированном PostgreSQL 17:

- БД создана опубликованным Linux Cosmic 0.26.0, зарегистрирован игрок, затем
  выполнен перенос новым Cosmic: сохранены OID всех **226** отношений и хеши
  строк пользователей, кораблей, систем, планет, каталога и каналов Chat.
  Проверка до переноса и повторный запуск прошли без изменения этих данных.
- Проверены OID/FK/owned sequence, секции, сохранение SELECT и перенос USAGE без
  CREATE; занятая целевая схема отвергается. Искусственная ошибка после перемещения
  откатывает перенос, новые схемы и маркер.
- Две установки, включая имя с кавычками и SQL-символами, остаются изолированными.
  Проверены ограниченные роли Planet и Chat, повторный startup с владельцем
  функций `chat_definer`, создание новой галактики и будущих секций Chat.
- Готовые Linux-сборки 0.27.0 из `downloads` запущены отдельными процессами
  с одним общим TOML и выключенным NATS: Cosmic `ok`, Planet/Chat `ready`,
  создано 13 схем, `--check-schemas` прошёл до и после миграции.
- Chromium: настоящие Cosmic/Planet/Chat и PostgreSQL, высадка, мышь, WASD,
  одинаковая диагональная скорость, ввод в Chat, коллизии, повторный вход,
  предложение/отмена/подтверждение перехода сектора. JS-ошибок не было.

Рабочая БД владельца из облачной среды не изменялась. Сборка Windows проверяется
как PE amd64; выполнение служб под Windows в этой среде недоступно.
