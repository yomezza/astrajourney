# Реализация Chat Service · 0.24.0

Состояние документа: 5 ноября 2026 года. Полный код интеграции находится в Go-службах и встроенном web-интерфейсе; демонстрационный HTML v13 остаётся отдельным исходным макетом.

## Что изменено

`internal/chat` отвечает за собственные транзакции, сообщения, доступ, приглашения, избранное, прочтение, жалобы и очистку. `internal/chatserver` — HTTP/WS, жизненный цикл, зависимости и допуск запросов. `internal/chatintegration` содержит Cosmic-owned миграционные/интеграционные функции, fences и обслуживание секций. `cmd/cosmosimulator-chat` поддерживает консоль, Windows SCM и команды DBA/обслуживания. Общие UUID-проверки вынесены в `platform/identifiers`; новая служба не импортирует планетарный транспорт или `internal/server`.

Cosmic остаётся владельцем пользователей/ролей/корпораций, глобальной географии и миграций. Planet остаётся владельцем визитов и подтверждает их свежесть сам. Chat не заводит вторую таблицу пользователей или присутствия и не меняет игровые кошельки/корабли. Для SQL row-locks используются отдельные защищённые функции с ограниченным NOLOGIN-владельцем; runtime не получает UPDATE игровых источников. Изменение корпоративного членства/прав обязано обновить fence в той же транзакции. Триггеры поддерживают именно эту ревизионную целостность, политика остаётся в обработчиках.

Роспуск корпорации переводит её в `deleting`; HTTP отвечает `202/deleting`, не сообщает о завершённом удалении. Chat очищает свою историю, выдаёт квитанцию; только затем Cosmic отделяет участников/станции и возвращает остаток средств ровно один раз. Удаление планетарной поверхности также ожидает квитанцию пространственной очистки.

Frontend использует существующие окна, контекстные меню, настройки, session lifecycle и стили. Переключение в домашнее закрепление перемещает один DOM-экземпляр с одним WebSocket, не создаёт дубликат. Фон меняет альфа-канал, текст остаётся непрозрачным. Уведомления, прочтение и доступ приходят из реальных серверных данных, автоматического принятия приглашений или фиктивной модерации макета нет.

## Найденные и устранённые проблемы

| Проблема | Решение |
|---|---|
| SQL `FOR SHARE` требует прав UPDATE на исходной таблице | Узкие SECURITY DEFINER функции; у runtime только EXECUTE, пароль/сессии напрямую недоступны |
| После выхода из корпорации старый WS мог доверять прежнему членству | Проверка fence и актуального источника в каждой транзакции |
| Новый планетарный визит некоторое время не имел свежего подтверждения | Planet записывает `checked_at` при входе/возобновлении; проверка живого WS обновляет его ограниченно по времени |
| Повтор сетевого запроса мог создать второе сообщение | UUID + digest + результат в одной транзакции; ACK после COMMIT, неопределённый исход выясняется чтением статуса |
| Больший outbox ID может закоммититься раньше меньшего | Перекрывающее окно доставки на срок больше ограниченной транзакции, отдельный отпечаток доступных событий |
| Обновление переписки сбрасывало чтение старой истории | Сохранение положения прокрутки; автоматический переход вниз только из нижнего положения |
| Кнопка закрытия эмодзи внутри формы могла отправить черновик | Явный `type=button`; палитра остаётся открыта при выборе символов |
| Резервная копия до модераторского удаления возвращает исходный текст | Внешний fsync-журнал только с UUID и проверкой установки; очистка до допуска запросов, отказ запуска при утрате журнала |
| `pg_restore --clean` пытается отдельно удалить наследуемые ограничения секций | Проверенный сценарий восстановления в пустую принадлежащую тесту схему |

## Проверки

Полный прогон `go test ./...` завершился без ошибок (130 верхнеуровневых сценариев, включая вложенные проверки); `go vet ./...` — без замечаний. Отдельно пройдены race-проверки операций/корпоративных fences/доставки/50 WS/пространственного присутствия и 64 общих UI-контракта. После завершающих изменений повторно проверены Chat-контракты с реальным Chromium и PostgreSQL.

Проверки БД выполняются только в одноразовых базах с суффиксом `_test`, с собственными схемами. Подтверждены сценарии:

- авторизация, приоритет первой WS-сессии, отбрасывание устаревшего поколения и запрет чужого Private;
- повтор операции и конфликт UUID/payload, Unicode-ограничения и серверные интервалы отправки;
- встречные приглашения в один DM, переход DM в группу с той же историей, новый DM после освобождения пары, нулевой исторический unread;
- видимые квитанции чтения, обычное удаление с сохранением копии, модераторское удаление с очисткой копий;
- ограниченная роль PostgreSQL: реальная отправка/чтение через функции при запрете UPDATE игровых таблиц, прямого `FOR SHARE` и чтения паролей;
- конкурентные отправки и отзыв членства, корпоративные ограничения и роспуск с однократным возвратом;
- пространственные сообщения с настоящим входом на планетарную службу, запрет чтения из космоса, квитанция очистки поверхности без изменения географии со стороны Chat;
- поиск в 100 002 строках: RU/EN, Ё/ё, буквальные `%`, `_`, `\`; выборочный EXPLAIN использует Bitmap Index Scan;
- 50 реальных авторизованных WebSocket-подключений и 50 записей через same-origin proxy;
- реальный `pg_dump`/`pg_restore` снимка до удаления: оригинал, locator и сохранённая копия очищены при восстановлении; отсутствие внешнего журнала блокирует допуск;
- Chromium с PostgreSQL: отправка/избранное, шесть вкладок, единый экземпляр/WS при закреплении, прозрачность текста, палитра, ширины 375/900/1280/1440; общие UI-контракты терминала.

Эти сценарии не являются доказательством всех возможных сочетаний тестовой матрицы 11 и не заменяют нагрузочное измерение на пользовательской Windows-машине. Скорость короткой серии в Linux не используется как обещание количества игроков. Windows EXE проверяются сборкой и контрольными суммами; реальный SCM требует проверки на целевой ОС.

## Эксплуатационные условия

Дневные/недельные секции обслуживаются отдельной задачей `--maintain` или явно настроенным отдельным соединением. Не использовать runtime как владельца схемы. Внешний журнал нужно защищать и сохранять актуальным независимо от снимков PostgreSQL: он хранит намерение модераторского удаления до SQL COMMIT, поэтому при аварии запись будет повторена даже при потерянном подтверждении операции. Обычные удаления и TTL сохраняют независимое избранное.

Логи/операционные квитанции не содержат снимков body. Текущий поиск ограничен доступной областью и временем запроса; короткий поиск общих каналов охватывает последние 1000 записей. История выдаётся страницами по 50. Списки справочных объектов/папок/бесед ограничены размером ответа, а не новой игровой квотой на создание.
