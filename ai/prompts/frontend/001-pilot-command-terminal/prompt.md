**Роль:** frontend  
**Идентификатор:** `001-pilot-command-terminal`  
**Статус:** **подготовлено к отдельному поручению владельца**. Сам факт хранения промпта **не разрешает** менять код.  
**Рабочая ветка при запуске:** `experiment/pilot-command-terminal` (или явно назначенная владельцем).  
**Каноническая идея:** [README.ru.md](../../../../docs/ideas/pilot-command-terminal/README.ru.md)  
**Технические рекомендации архитектора:** [02-frontend-architecture-prototype.ru.md](../../../../docs/ideas/pilot-command-terminal/02-frontend-architecture-prototype.ru.md)  
**Общие правила:** [AGENTS.md](../../../../AGENTS.md)

## Задача после получения команды

Создай **реально интерактивную**, но строго **изолированную** пробу единого командного терминала Astra Journey в `scripts/frontend-generation/`.

**Не заменяй рабочее меню** и не делай новую игру или чистый статичный макет. Используй существующий дизайн, CSS, SVG, оконный менеджер/оболочку демосреды, по возможности уже имеющуюся UI/UX-лабораторию.

Цель — проверить, удобны ли игроку вкладки персональных рабочих пространств, где одинаковые модули могут независимо показывать разные корабли.

## Обязательно прочитать

- `AGENTS.md`, `README.md`, каноническую идею и **архитектурное приложение** по ссылкам выше.
- Актуальные `internal/server/web/ui/windows.js`, `features/shell/navigation.js`, `features/fleet/`, `features/mining/`, `core/preferences.js`.
- `scripts/frontend-generation/README.md`, доступные mock-данные, frontend-лабораторию.

Изучи **актуальный `main`**, не полагайся на старые списки файлов/модулей.

## Что должно работать

1. **Вкладки рабочих пространств:** создание, переименование (1–32 видимых символа), выбор, удаление с защитой последнего, дублирование, перестановка. Ограничение **10** на пользователя.
2. **Каталог модулей:** добавить экземпляр в активную вкладку, найти модуль по названию. Для пробы достаточно «Корабль», «Трюм», «Добыча», «Справка».
3. **Разные экземпляры одного типа:** в «Добыча — 1» корабль `shipId=41`, в «Добыча — 2» — `shipId=82`. Оба объекта называются «Пилигрим». Выбор в одной вкладке не портит другую.
4. **Контекст:** в заголовке пространства виден его корабль; у каждого связанного окна выбор `workspace` (следовать контексту), `fixed` (выбранный ID), а для независимых модулей — `none`.
5. **Настоящие интерактивные окна:** открытие/активация, перемещение, изменение размера, скрытие, удаление из рабочего пространства; переключение вкладок восстанавливает геометрию.
6. **Сохранение через браузер:** JSON с версией и разделением по тестовому пользователю; перезагрузка страницы восстанавливает вкладки, контекст и доступное UI-состояние. Не сохранять кредиты/грузы как истину.
7. **Негативные сценарии:** 11-я вкладка, слишком длинное имя, потерянный mock-корабль, нет прав к модулю, обычное обновление страницы, тесная ширина браузера.
8. **Удобство:** сохранять принятый космический стиль, дать возможность сравнить новую пробу с оригинальной навигацией, показать понятные названия и маркеры привязки.

## Критические ограничения

- **Ни одного изменения production** `internal/server/web/`, Go, PostgreSQL, API, NATS, `downloads/` или релизов.
- **Не менять** `Session.data.expedition.ship` и реального активного корабля при переключении вкладок.
- **Не выполнять** настоящий `performExpedition`, `select_ship` и другие игровые команды ради демо. Только mock-функциональность.
- Не копировать singleton production `createFleet()`/`createMining()` в несколько корней без их анализа: они используют общие селекторы и состояние. Для пробы допустим **тонкий demo-адаптер с уникальными instance ID**, как указано в архитектурном приложении.
- Чат, уведомления и системные диалоги не создавать по 10 независимых экземпляров без необходимости. Их глобальное поведение — предмет оценки, а не уже согласованный production-контракт.
- Не добавлять React/Vue или тяжёлые библиотеки ради вкладок.
- Если текущая демосреда изменилась, сохрани её действующие демонстрации и не переписывай ради нового режима.

## Проверка результата

Предоставь живой адрес/способ локального запуска и конкретный сценарий: два пространства с одноимёнными кораблями 41/82 → разные контексты «Добычи» и «Трюма» → переключение туда-обратно → перезагрузка → восстановление. Отдельно проверь сообщения об ошибках/недоступном объекте.

## Отчёт

- Ветка, SHA коммита, изменённые файлы, PR (если создавался).
- Какие UI-сценарии реально проверены; какие нет.
- Как войти в экспериментальную страницу и вернуться в штатную демосреду.
- Что осталось нерешённым и какой рефакторинг понадобился бы для **отдельно разрешённого** production-внедрения.

**Не внедрять пробу в настоящую игру без новой команды владельца.**
