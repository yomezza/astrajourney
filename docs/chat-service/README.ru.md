# Chat Service · 0.24.7

Отдельная служба `cosmosimulator-chat.exe`, общая PostgreSQL и существующие игровые аккаунты. Исходные утверждённые требования и макет v13 сохранены в [docs/ideas/chat-service](../ideas/chat-service/README.ru.md). Продуктовые правила 01/02 имеют приоритет перед ранними техническими предложениями: обычное удаление беседы/корпорации сохраняет независимые копии в избранном; модераторское удаление конкретного оригинала удаляет связанные копии.

## Запуск под Windows

С версии 0.24.4 вместо перечисленных ниже переменных можно задать только
`CONFIG_FILE` с путём к TOML. Файл становится единственным источником настроек
приложения. [Шаблоны и инструкция](../configuration.ru.md). Для SCM путь задаётся
в окружении самой службы. При выбранном TOML включение чата в Cosmic задаётся
как `cosmos.chat_enabled = true`, адрес — `cosmos.chat_internal_url`.


1. Сохранить резервную копию общей БД. Использовать одну существующую базу и одинаковый `DB_SCHEMA` во всех службах.
2. Для космической службы установить `CHAT_ENABLED=true`, обновить и запустить Cosmic. Она применяет `schema240.sql`, функции доступа и создаёт начальные секции сообщений. Нужны PostgreSQL 17 с ICU, UTF-8 и `pg_trgm`; расширение предварительно может установить DBA. Планетарная служба сохраняет marker 7, география не пересоздаётся.
3. Настроить Chat и запустить третью сборку:

```powershell
$env:CHAT_DATABASE_URL = 'postgres://chat_runtime:YOUR_PASSWORD@127.0.0.1:5432/YOUR_DATABASE?sslmode=disable'
$env:DB_SCHEMA = 'cosmosimulator'
$env:CHAT_HTTP_ADDR = '127.0.0.1:8082'
$env:COSMIC_INTERNAL_URL = 'http://127.0.0.1:8080'
$env:PLANET_INTERNAL_URL = 'http://127.0.0.1:8081'
$env:CHAT_ALLOWED_ORIGINS = 'http://YOUR_GAME_HOST:8080'
$env:CHAT_ERASURE_JOURNAL = 'C:\Cosmosimulator\data\chat-erasure.log'
.\downloads\cosmosimulator-chat-v0.24.9-windows-amd64.exe
```

Каталог журнала должен существовать. Служебному аккаунту Windows нужен доступ к файлу; другим аккаунтам доступ ограничить. Браузер обращается к Cosmic `/chat/api/v1/*` и `/chat/ws/v1`; открывать порт 8082 наружу не требуется. В Cosmic при необходимости задать `CHAT_INTERNAL_URL`. Для сайта за HTTPS указывать точный HTTPS Origin. `DATABASE_URL` используется как запасной адрес Chat, если не задан `CHAT_DATABASE_URL`.

SCM поддерживается с именем `CosmosimulatorChat`:

```powershell
sc.exe create CosmosimulatorChat binPath= 'C:\Cosmosimulator\cosmosimulator-chat-v0.24.9-windows-amd64.exe' start= auto
sc.exe start CosmosimulatorChat
```

Переменные среды должны быть доступны служебному аккаунту при запуске SCM. Присвоение `$env:...` действует только в текущем PowerShell; для постоянной службы настроить постоянное окружение/перезапустить SCM-хост согласно своей схеме эксплуатации.

## Обычный HTTP в локальной сети: пример диагностики

Если Chat слушает только `192.168.111.44:8082`, значение по умолчанию
`CHAT_INTERNAL_URL=http://127.0.0.1:8082` в Cosmic к нему не подключится.
В окружении **космического процесса**, дополнительно к его настройкам БД и Planet:

```powershell
$env:CHAT_ENABLED = 'true'
$env:CHAT_INTERNAL_URL = 'http://192.168.111.44:8082'
```

После настройки остановить старый Cosmic и запустить новую сборку из этого
PowerShell. Для SCM-службы эти значения должны быть заданы именно в её окружении,
затем службу нужно перезапустить: `$env:` в отдельной консоли не меняет среду уже
работающего процесса или службы. Надпись «Отключена» означает, что запущенный
Cosmic не видит `CHAT_ENABLED=true`; неверный адрес связи даёт «Нет связи».

Chat должен иметь обратные адреса `COSMIC_INTERNAL_URL=http://192.168.111.44:8080`
и `PLANET_INTERNAL_URL=http://192.168.111.44:8081`, а
`CHAT_ALLOWED_ORIGINS=http://192.168.111.44:8080` задаёт адрес сайта в браузере.
В значениях URL используются обычные `http://`, без обратных слешей.

Проверки выполняются на машине, где запущены службы:

```powershell
Invoke-RestMethod 'http://192.168.111.44:8080/api/health'
Invoke-RestMethod 'http://192.168.111.44:8081/planet/api/v1/health/ready'
Invoke-RestMethod 'http://192.168.111.44:8082/chat/api/v1/health'
```

В последнем ответе `ready` и `cosmic` должны быть `true`; `planet` показывает
доступность планетарной службы. Проверки не требуют браузерной сессии. Вызов
Chat health возвращает HTTP 503, если Chat ещё не готов; это отличается от
отсутствия TCP-соединения. Браузер по-прежнему использует порт Cosmic, не 8082.
С версии 0.24.3 внутренние запросы этих служб и gateway не используют системный
`HTTP_PROXY`; это не отключает проверки TLS.

Если всё работает на одной машине, можно вместо LAN-адресов согласованно
настроить внутренние слушатели и все внутренние URL на `127.0.0.1`.
`*_ALLOWED_ORIGINS` при этом остаются равны адресу сайта, который открывает игрок.

С версии 0.24.3 UUID команд чата, высадки и возвращения создаются через
`crypto.getRandomValues`, доступный и на обычном HTTP по LAN IP. Ошибка
`crypto.randomUUID is not a function` больше не прерывает эти действия.
После замены Cosmic обновить страницу, чтобы загрузился новый JavaScript.

Ответы HTTP 401 относятся к авторизации, а не к firewall. При постоянных 401
после входа проверить передачу сессионного cookie и настройку `COOKIE_SECURE`:
для этого локального HTTP-примера Secure-cookie не подходит; для публичного
доступа использовать HTTPS и `COOKIE_SECURE=true`.

Сообщение CSP об inline-скрипте `VM…` само по себе не позволяет определить
источник кода. Штатный клиент использует внешние ES-модули; разрешать
`unsafe-inline` для устранения ошибок UUID не требуется.

## Права PostgreSQL

Не выдавать Chat логин Cosmic/Planet для изменения игровых таблиц. Создать отдельные роли через DBA:

```sql
CREATE ROLE chat_runtime LOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE;
CREATE ROLE chat_definer NOLOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE;
```

Установить пароль логину безопасным способом и дать CONNECT к выбранной БД. После миграции выполнить сборкой Chat **однократную команду DBA** с административным `DATABASE_URL`:

```powershell
$env:CHAT_RUNTIME_ROLE = 'chat_runtime'
$env:CHAT_DEFINER_ROLE = 'chat_definer'
.\cosmosimulator-chat-v0.24.9-windows-amd64.exe --grant-runtime
```

Команда выдаёт права на чат, ограниченное чтение игровых данных и EXECUTE на защищённые функции. Владельцем этих функций становится отдельная NOLOGIN-роль; PUBLIC execute отозван, `search_path` фиксирован. Логин runtime не получает UPDATE пользователей, корпораций, присутствия или fences и не читает пароли/сессии напрямую. После команды убрать DBA-реквизиты из окружения Chat. При последующих миграциях DBA/migration-роль должна иметь право заменять функции, принадлежащие `chat_definer`; повторить выдачу прав после обновления контракта.

Fences принадлежат Cosmic. Небольшие триггеры поддерживают их ревизию при всех изменениях членства/ролей/владельца в той же транзакции. Проверка политики находится в Go и узких функциях, переписка не хранится в игровых таблицах.

## Ежедневное обслуживание секций

Chat runtime не выполняет DDL. Запланировать ежедневную отдельную задачу Windows Task Scheduler с отдельными реквизитами владельца секций:

```powershell
$env:CHAT_MAINTENANCE_DATABASE_URL = 'postgres://PARTITION_OWNER:YOUR_PASSWORD@127.0.0.1:5432/YOUR_DATABASE?sslmode=disable'
.\cosmosimulator-chat-v0.24.9-windows-amd64.exe --maintain
```

Она создаёт дневные секции на 14 дней и недельные на 8 недель вперёд, удаляет полностью просроченные пустые секции. Владельцу обслуживания нужны права на родительские таблицы/секции и CREATE в выбранной схеме; это **не** runtime-логин. Опционально `CHAT_MAINTENANCE_DATABASE_URL` запускает обслуживание внутри процесса раз в час; для строгого разделения реквизитов использовать отдельную задачу. Без обслуживания начальный запас секций закончится, отправка сообщений будет отклонена; не заменять эту ошибку записью в произвольную секцию.

Удаление истёкших сообщений/приглашений и продолжение очистки бесед выполняется runtime-работником каждые 10 секунд ограниченными порциями. История и поиск дополнительно фильтруют срок хранения на чтении.

## Отказы и восстановление

Один действующий Chat WS на аккаунт; первая вкладка сохраняет приоритет. При отключении Cosmic весь пользовательский чат недоступен. Отказ Planet закрывает только Planet/Sector. Проверка служб каждые 2 секунды; единичный неуспешный ответ не отменяет прежнее успешное состояние, после повторного сбоя доступ закрывается. Устаревшее подтверждение здоровья также закрывает доступ. В административном «Статусе служб» есть третья карточка.

Журнал `CHAT_ERASURE_JOURNAL` содержит только UUID модераторских удалений, идентификатор установки и фиксируется на диске до SQL-удаления. Хранить его отдельно от снимков БД и резервировать непрерывно; не восстанавливать старую копию журнала поверх актуальной. На старте проверяются принадлежность установки и сохранённый счётчик, повторяются удаления оригиналов/копий. Потерянный, повреждённый или несоответствующий журнал блокирует запуск. Не создавать пустой журнал для существующей переписки. При утрате журнала требуется проверенное восстановление WAL/PITR и ручная сверка DBA; автоматического обхода этой защиты нет.

В одном развёртывании запускается один процесс Chat, защищённый блокировкой PostgreSQL. Во время восстановления сначала остановить Chat. Для восстановления схемы с секциями использовать пустую целевую схему/БД: `pg_restore --clean` может пытаться отдельно удалить наследуемые ограничения секций. Обязательно сохранить текущий внешний журнал и запустить повторную очистку до открытия доступа игрокам.

Полный протокол и проверенные сценарии: [API](API.ru.md), [отчёт](REPORT.ru.md).

## Общий диспетчер N1

Chat 0.24.7 сохраняет `legacy` по умолчанию. A1 включается только явно:
`chat.dispatcher_mode = 'a1'` в отдельном TOML Chat либо
`CHAT_DISPATCHER_MODE=a1` в ENV-режиме. Это общий bounded outbox scanner и
локальные postcommit уведомления, без NATS/JetStream. Перезапускается только Chat.

При A1 по-прежнему выполняются авторизация/проверка scope каждые 2s и проверки
WS lease; HTTP/WS протокол и SQL read/write ACL сохранены. `[nats]` не поддерживается.
Для отката выбрать `legacy` и перезапустить Chat с прежним erasure journal.

Новые параметры нельзя добавлять в общий файл, используемый прежними EXE
Cosmic/Planet: их строгий decoder не знает этих полей. Для Chat нужна отдельная
копия TOML. [Отчёт, измерения и проверки](../operations/nats-n1/README.ru.md).


## PostgreSQL LISTEN/NOTIFY N2 (Chat 0.24.8)

Добавлен `dispatcher_mode = 'a2'` в существующую секцию `[chat]` отдельного
TOML Chat; в ENV-режиме — `CHAT_DISPATCHER_MODE=a2`. `legacy` остаётся default,
`a1` сохранён. NATS и `[nats]` не подключены.

A2 использует один выделенный PostgreSQL-сеанс, канал
`cosmos_chat_<md5(DB_SCHEMA)>`, переподписку и обязательный резервный polling.
Пустой NOTIFY только будит прежний общий диспетчер; ACL остаются в SQL.
Каждые 30s A1/A2 дополнительно перепроверяют действующие session/WS lease
и отправляют общий `sync`, чтобы восстановить текущее состояние даже при
позднем COMMIT вне overlap. Это не replay каждого исторического события.

**N2 разрешён только на изолированном стенде.** Chat не создаёт A2 SQL-объекты.
Проект DBA-триггера требует отдельного согласованного внедрения владельцем
миграций; действующая цепочка Cosmic не изменена. Без триггера LISTEN может
зарегистрироваться, но сообщения обнаруживаются только polling. Поле
`wake_source.healthy` в логах означает зарегистрированное соединение,
а не подтверждённую установку или доставку от триггера.

[Полный отчёт, функциональные проверки и rollback](../operations/nats-n2/README.ru.md).


## Core NATS N3 (Chat 0.24.9)

Добавлен `dispatcher_mode = 'b1'` с отдельной секцией `[nats]` в **Chat TOML**.
По умолчанию остаётся `legacy`, NATS отключён. A1/A2 сохранены. B1 использует
только `cosmos.v1.signal.chat.outbox.changed`, после COMMIT, без текста
переписки. Подписка с проверкой envelope будит прежний общий SQL dispatcher;
резервный polling и независимая сверка 30s продолжают работать.

Клиент проверяет TLS CA/SAN и static login `chat`; пароль только из защищённого
`password_file`. Брокер недоступен — игра работает через SQL, source degraded.
Подключение и подписка автоматически восстанавливаются. Другие subjects,
Planet/Cosmic events, Request/Reply и JetStream не внедрялись.

**Рабочий cosmoNATS не менялся и к нему не подключались.** Перед первым
подключением требуется подготовка TLS/auth/ACL на Windows по отдельному
согласованию. Не переносите тестовый конфиг брокера поверх действующего.

[Полный отчёт N3, выполненные проверки и откат](../operations/nats-n3/README.ru.md).
