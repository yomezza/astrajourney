# Astra Journey — перенос модулей «Исследования» и «Колонии» из frontend-демосреды в production

Ты — Backend-разработчик проекта Astra Journey (Cosmosimulator).

**Репозиторий:** https://github.com/yomezza/cosmosimulator

## 1. Задача

Необходимо перенести в рабочий production-интерфейс Astra Journey две уже разработанные и согласованные frontend-реализации:

1. **Исследования** — обновлённый каталог звёздных систем и экран «Подробнее».
2. **Колонии** — переработанный двухколоночный интерфейс управления колониями и проектами.

Эти интерфейсы созданы frontend-разработчиком в отдельной демонстрационной среде:

`scripts/frontend-generation/`

**Не нужно проектировать их заново, менять визуальную концепцию или придумывать альтернативную реализацию.**

Твоя задача — изучить готовые исходники, адаптировать их к production, сохранить игровую функциональность и проверить корректность интеграции с существующим backend.

В отличие от frontend-разработчика, тебе разрешается изменять production-файлы в рамках этой конкретной задачи.

Однако любые изменения Go, PostgreSQL, игровых API или общей архитектуры должны быть отдельно обоснованы. Предпочтительный результат — frontend-интеграция без изменения игровых контрактов.

---

## 2. Важная архитектурная договорённость

В проекте принято следующее разделение ответственности.

### Frontend-разработчик

Работает исключительно внутри:

`scripts/frontend-generation/`

Здесь создаются и проверяются новые интерфейсы, прототипы, компоненты и варианты дизайна.

Frontend-разработчик не должен напрямую изменять:

- `internal/server/web/`
- Go-код
- PostgreSQL
- игровые API
- production-конфигурацию

### Backend-разработчик

После утверждения интерфейса владельцем проекта выполняет его перенос из демосреды в production.

При переносе:

- использует утверждённую frontend-реализацию как визуальный эталон;
- подключает реальные игровые данные;
- сохраняет действующие серверные правила;
- обеспечивает совместимость со штатными игровыми модулями;
- выполняет интеграционные проверки;
- не переносит mock-операции в production.

**Это принципиальное разделение: экспериментальная frontend-разработка и production-интеграция не должны смешиваться.**

# Часть I. Модуль «Исследования»

## 4. Что разработано frontend-разработчиком

Основные файлы демоверсии:

- `scripts/frontend-generation/prototype/studies/app.js`
- `scripts/frontend-generation/prototype/studies/system-view.js`
- `scripts/frontend-generation/prototype/studies/system-view.css`

Frontend-разработчик реализовал обновлённый интерфейс исследований, использующий существующие игровые визуальные компоненты и SVG-ассеты.

### Каталог исследований

В интерфейсе предусмотрены:

- список исследованных звёздных систем;
- выделение выбранной системы;
- поиск;
- фильтрация;
- отображение текущей системы корабля;
- кнопка «На карте»;
- кнопка «Подробнее»;
- сохранение состояния каталога при возврате из подробного просмотра.

Дизайн соответствует согласованной концепции «Исследования v13».

Не нужно заменять его стандартными таблицами или заново разрабатывать карточки.

## 5. Экран «Подробнее»

Frontend-разработчик создал отдельный экран просмотра состава звёздной системы.

Файл:

`prototype/studies/system-view.js`

### Как он работает

Объекты располагаются горизонтально:

**Звезда → планеты → другие объекты системы.**

Для каждого объекта используются готовые SVG из проекта.

Поддерживаются:

- звёзды спектральных классов O, B, A, F, G, K, M;
- каменистые планеты;
- садовые миры;
- пустынные планеты;
- ледяные планеты;
- лавовые и вулканические планеты;
- газовые гиганты;
- орбитальные станции;
- пояса астероидов;
- ледяные поля;
- предусмотренные реестром дополнительные объекты.

Внешний вид включает увеличенные космические объекты, тёмный фон, звёздные точки и тонкую координатную сетку.

Реализованы горизонтальная прокрутка, подписи объектов, всплывающие подсказки, работа с мышью и клавиатурой, адаптация к небольшим экранам.

### Важные технические решения

Frontend-разработчик использовал обычные HTML-элементы и SVG-изображения.

Не использовались React, Vue, Three.js или дополнительный 3D-движок.

Изображения выбираются по типу объекта. Для неизвестного типа предусмотрен нейтральный fallback `object-unknown.svg`.

Объекты не генерируются произвольно.

### Источник данных

В демоверсии используется существующий HTTP-контракт:

`GET /api/system?id=ID`

Демонстрационный сервер отвечает на него через общий mock-реестр.

В production необходимо использовать **реальный существующий API**, сохранив его права доступа и правила раскрытия исследовательской информации.

Категорически запрещается раскрывать игроку неизвестные или неоткрытые объекты только ради визуального отображения.

## 6. Что необходимо сделать с «Исследованиями»

1. Сравнить демоверсию с текущими production-файлами:

   - `internal/server/web/features/research/index.js`
   - `internal/server/web/features/research/system-view.js`
   - `internal/server/web/styles/research-system.css`

2. Перенести недостающие визуальные и интерактивные элементы.
3. Встроить экран «Подробнее» в существующий жизненный цикл модуля.
4. Использовать реальные игровые данные и штатные API.
5. Сохранить текущую интеграцию с галактической картой.
6. Проверить сохранение поиска, фильтров и выбранной системы при возвращении.
7. Проверить загрузку всех SVG и отсутствие ошибок путей.
8. Проверить горизонтальную прокрутку, tooltip и адаптивность.

**Ожидаемый результат:** production-модуль визуально и функционально соответствует согласованной демоверсии.

# Часть II. Модуль «Колонии»

## 7. Что разработано frontend-разработчиком

Основная демонстрационная реализация:

- `scripts/frontend-generation/mock/colony-catalog.js`
- `scripts/frontend-generation/mock/colony-catalog.css`

В отличие от старого списка проектов, новый интерфейс построен по образцу «Исследований».

Он имеет двухколоночную компоновку.

### Левая часть — выбранная колония

Показывает:

- крупную SVG-планету;
- название планеты или проекта;
- звёздную систему;
- тип планеты, если известен;
- владельца;
- сектор;
- статус проекта;
- доступные сведения о строительстве и колонизации;
- действия с проектом и поверхностью.

### Правая часть — каталог

Показывает:

- список существующих колоний и проектов;
- поиск;
- выделение выбранной карточки;
- информацию о владельце и статусе;
- переключение выбранного проекта без создания лишних окон.

На небольших экранах колонки адаптируются к доступному пространству.

### Как реализована графика

Frontend-разработчик использовал существующие SVG:

- `object-rocky.svg`
- `object-garden.svg`
- `object-desert.svg`
- `object-icy.svg`
- `object-lava.svg`
- `object-gas.svg`

И другие предусмотренные проектом ассеты.

Для отсутствующей информации или неизвестного типа применяется нейтральное изображение.

Не нужно генерировать новую планету, если у проекта уже есть соответствующий астрономический объект.

## 8. Откуда берутся данные

В демоверсии использованы существующие структуры API.

Основные источники:

`GET /api/planet/projects`

и

`GET /api/system?id=ID`

Первый предоставляет проекты и возвраты.

Второй позволяет сопоставить проект с астрономическим объектом и получить доступные сведения о планете.

Сопоставление должно выполняться по числовым идентификаторам, а не по названию планеты.

В production необходимо учитывать реальную структуру ответов, права доступа и возможное отсутствие информации.

Не создавай дополнительные API или поля без подтверждённой необходимости.

## 9. Какие функции необходимо сохранить

Новый интерфейс — это изменение представления, а не игровой логики.

Обязательно сохранить штатные операции:

- открытие проекта колонизации;
- просмотр поверхности планеты;
- продолжение высадки;
- получение возвратов;
- работу с существующими состояниями проектов;
- финансирование;
- строительство;
- отмену проекта, если она разрешена игровыми правилами;
- административные операции, доступные по соответствующим правам.

Нельзя заменять настоящие игровые операции mock-кнопками.

Однако нельзя и переносить демонстрационные обработчики напрямую в production.

**Все действия должны вызывать существующие production-функции с сохранением их проверок и ограничений.**

### Что проверить перед переносом

В production уже могут существовать:

- `internal/server/web/features/planet/colony-catalog.js`
- `internal/server/web/styles/colony-catalog.css`

Ранее создавалась общая реализация каталога для демоверсии и production.

Проверь их актуальность, фактическое подключение, совпадение с демоверсией и работу на реальном API.

Если перенос уже частично выполнен, необходимо завершить и проверить интеграцию, а не создавать вторую копию модуля.

# Часть III. Общие технические требования

## 10. Использовать существующую архитектуру

Frontend-разработчик намеренно использовал:

- Vanilla JavaScript;
- штатные CSS-переменные Cosmosimulator;
- существующий оконный менеджер `Modules`;
- действующие UI-компоненты;
- оригинальные SVG-ассеты;
- реальные схемы объектов;
- существующие маршруты API.

Продолжай в том же направлении.

Запрещается создавать второй оконный менеджер, альтернативную систему авторизации или собственный frontend-фреймворк ради переноса двух модулей.

## 11. Не смешивать mock и production

Демосреда содержит вымышленные данные и безопасные адаптеры.

В production нельзя переносить:

- фиктивные корабли;
- фиктивные колонии;
- вымышленные игровые ресурсы;
- демонстрационные ответы Python mock API;
- функции, предназначенные исключительно для тестовых действий;
- искусственное изменение прав или статусов исследования.

Переносить нужно **интерфейс, компоненты, CSS, поведение элементов и подходящие адаптеры**.

Игровые данные и операции должны поступать из существующих production-источников.

## 12. Совместимость

После переноса должны продолжать работать:

- штатный оконный менеджер;
- галактическая карта;
- исследование систем;
- планетарная поверхность;
- высадка;
- создание и управление проектами колонизации;
- чат;
- уведомления;
- остальные игровые модули.

Особенно проверь, что изменения CSS не затрагивают посторонние окна.

Обработчики прокрутки должны удерживать прокрутку внутри модульного окна и не переключать её на главную страницу.

# Часть IV. Проверки

## 13. Обязательные сценарии

### Исследования

- Открыть каталог исследований.
- Выбрать известную систему.
- Открыть «Подробнее».
- Проверить реальные объекты и их порядок.
- Проверить все доступные типы SVG.
- Проверить tooltip.
- Проверить горизонтальную прокрутку.
- Вернуться назад.
- Убедиться, что поиск, фильтр и выбранная система сохранились.
- Проверить поведение неизвестной или частично исследованной системы.
- Проверить доступность на небольшом экране.

### Колонии

- Открыть список проектов.
- Выбрать проект.
- Проверить соответствие планеты и проекта по ID.
- Проверить SVG.
- Переключить выбранный проект.
- Открыть проект колонизации.
- Открыть поверхность планеты.
- Проверить доступные операции с проектом.
- Проверить возвраты.
- Проверить пустой каталог.
- Проверить сценарий отсутствующей информации о планете.
- Проверить, что права и ограничения не обходятся.

### Общие проверки

- Проверить JavaScript в браузере на отсутствие ошибок.
- Проверить загрузку CSS и ассетов.
- Проверить производительность.
- Проверить поведение окон после изменения размера.
- Проверить существующие unit/integration/browser tests.
- Добавить регрессионные тесты для затронутых механизмов.

Предпочтительно выполнить проверки на отдельном тестовом окружении с тестовыми данными. Рабочую БД не изменять ради тестирования интерфейса.

# Часть V. Порядок работы

1. Изучи демоверсию и текущий production.
2. Подготовь перечень различий по обоим модулям.
3. Определи, что уже перенесено и что отсутствует.
4. Выполни необходимую frontend-интеграцию в production.
5. Сохрани штатные API и бизнес-логику.
6. Проверь модули в браузере с реальными тестовыми ответами backend.
7. Исправь выявленные проблемы.
8. Выполни автоматизированные проверки.
9. Подготовь отчёт.
10. После успешных проверок опубликуй изменения в GitHub, ветка `main`.

Не останавливайся на анализе или подготовке плана. Ожидается завершённая интеграция.

Если обнаружится, что отдельные части уже существуют в production, не переписывай их без необходимости.

---

## 14. Итоговый отчёт

После выполнения сообщи:

1. Какие интерфейсные элементы перенесены из демосреды.
2. Какие из них уже были в production.
3. Какие production-файлы изменены.
4. Какие существующие игровые API используются.
5. Какие backend-изменения потребовались, если вообще потребовались.
6. Какие автоматизированные и браузерные проверки выполнены.
7. Какие проблемы обнаружены и исправлены.
8. Остались ли различия между демосредой и production.
9. SHA итогового коммита.

**Критерий завершения:** «Исследования» и «Колонии» в основной игре выглядят и работают как согласованные frontend-прототипы, но используют настоящие игровые данные, действия, ограничения и права доступа.

**Дополнительное правило:** не изменяй содержимое `scripts/frontend-generation/` в ходе переноса без отдельной необходимости и согласования. Это исходная демонстрационная среда и визуальный эталон для сравнения с production.

Главная цель — перенести утверждённый frontend в игру без дублирования реализации, потери существующей функциональности и вмешательства в игровую бизнес-логику.
