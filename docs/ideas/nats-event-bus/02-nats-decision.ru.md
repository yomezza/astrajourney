# NATS Event Bus — 02. Архитектурное решение B и критерии применения

Дата: 2026-11-09. Статусы: **УТВЕРЖДЕНО владельцем** — B как цель и два последовательных пилота; **ПРЕДЛОЖЕНИЕ** — конкретные параметры/контракты; **ЭКСПЕРИМЕНТ** — результаты A1/A2/B1 ещё отсутствуют.

## 1. Сравнение A/B/C/D

| Критерий | A: HTTP/WS+PostgreSQL | B: NATS signals + selective JetStream | C: B + Request/Reply | D: максимальный NATS |
|---|---|---|---|---|
| Сложность | низкая | средняя | высокая | очень высокая |
| Надёжность | известная, существующие гарантии | высокая при сохранённых DB/fallback | зависит от новых RPC | высокий риск новых failure modes |
| Производительность | полезны Go hub и PG NOTIFY | минимальная задержка signals; нужно измерить | RPC не обязательно быстрее HTTP | без гарантии ускорения |
| PostgreSQL | может уменьшить polling | может уменьшить polling, сохраняет обязательные проверки | близко к B | возможные дорогие read models |
| Задержка уведомлений | polling 2s либо NOTIFY | обычно меньше polling при подключённом NATS | как B | определяется всей цепочкой |
| Безопасность | действующая Origin/session/DB | + TLS/subject ACL | + RPC ACL/аудит | много новых зон доверия |
| Зависимость от NATS | отсутствует | мягкая для signals, не для действий | появляется у RPC | значительная |
| Масштабирование | ограничено дизайном приложения | независимые producers/consumers | облегчает некоторые маршруты | технически гибко, дорого |
| Диагностика | самая простая | event_id, metrics, reconnect | distributed trace/RPC timeout | самая сложная |
| Economic Service | нужен новый канал событий | готовые пространства для future outbox/JetStream | + возможность RPC при доказанной необходимости | overengineering |

**Решение:** B. C не запрещён навсегда; его ввод требует отдельного эксплуатационного сценария/бенчмарка и согласования. D отвергается для v1. A — необходимая измерительная база.

## 2. Нерушимые правила

1. PostgreSQL — источник истины пользователей, визитов, сообщений, возврата кораблей, корпоративных прав, cleanup requests/receipts.
2. HTTP и браузерные WS остаются, включая Cosmic reverse proxy. Не удалять внутренние URL из TOML на этом этапе.
3. NATS-сигнал не изменяет права пользователя, epoch, scope или транзакционное состояние. Только «перечитай источник».
4. Успех игровых операций возвращается после PostgreSQL COMMIT, не после Publish/Flush NATS.
5. Наличие соединения с NATS не доказывает готовность Cosmic/Planet. Их readiness и lease checks продолжают работать независимо.
6. Сбой Core NATS не останавливает штатные действия, которые уже имеют собственный durable PostgreSQL-контракт. Скорость UI-синхронизации деградирует к резервному polling.
7. JetStream не создаёт транзакции с PostgreSQL: для действительно обязательной передачи нужен **transactional outbox + publisher + PubAck + идемпотентный consumer + ack**. Простое двойное «INSERT и Publish» не даёт гарантии.
8. `CHAT_ERASURE_JOURNAL` — внешний fsync-журнал модерационных удалений. Не переносить туда JetStream и не заменять его.
9. Брокер не получает тела Private/Corporation сообщений, cookie, session hashes, пароли, причины модерации, содержимое backup.
10. Первые пилоты используют Core NATS только как оптимизацию; JetStream не требуется.

## 3. Жизненный цикл внедрения

- **P-NATS-01:** общий Go-диспетчер Chat, сравнение A1 (local+poll), A2 (PG LISTEN/NOTIFY+poll), B1 (Core NATS+poll). Права и разрешённые получатели во всех режимах идентичны. В результате эксперимента можно выбрать A2 для собственно Chat при одновременном применении Core NATS межсервисно.
- **P-NATS-02:** Planet sector transition → Core NATS сигнал → Chat invalidation + authoritative DB recheck; запуск только после P-NATS-01.
- **Расширение Cosmic → Chat:** быстрые invalidations ролей, модераторов, удаления корпораций — лишь после успешных пилотов.
- **JetStream:** будущие долговечные события Economic и другие задачи с объективной потребностью в replay, отдельный DBA/операционный контракт.

## 4. Сравнение Chat как эксперимент, а не предположение

| Коннектов | Текущих Changes()/s (из 2s таймера) | Предлагаемый общий safety-poll в штатном режиме |
|---:|---:|---:|
| 50 | 25 | 0.1 /s при периоде 10s |
| 100 | 50 | 0.1 /s |
| 200 | 100 | 0.1 /s |
| 256 | 128 | 0.1 /s |

Это **число пробуждений общей проверки outbox**, а не общая нагрузка PostgreSQL. Перепроверка пользовательской сессии, аудит scope, доступ к приватным каналам и HTTP история неизбежно добавят запросы. Нельзя объявлять «128 запросов превращены в 0.1 запроса» без измерения batched revalidation, выборки и обработки изменённых событий.

**Почему не 30s для основного fallback:** при пропуске единственного сигнала пользователь может ждать до 30s, а текущий сервис обычно делает это за <=2s. Кроме того, существующее overlap=15s несовместимо с механическим переходом к 30s polling при поздних COMMIT. Предлагаемая настройка пилота: safety polling 10s, переход на 2s при потере транспорта, аварийной переподписке или backlog; overlap 60s минимум, с проверкой по максимальному интервалу от event INSERT до COMMIT + period + jitter. 30s — отдельный эксперимент, не готовый дефолт.

## 5. Критерии допуска к следующей стадии

- Измерить latency от БД COMMIT до server sync и отдельно до GET/отрисовки истории, p50/95/99; считать потери и лишние уведомления.
- Наблюдать pg_stat_statements, CPU PostgreSQL, SQL wall time, CPU/RAM Go, число WS, queue depth, lag, broker reconnect.
- Отрицательные тесты на Private/Corporation/Planet/Sector, смену членства/epoch и истечение сессии.
- Проверить отказ NATS на 5 минут, рестарт, delayed lower-ID commit, late subscriber, WS slow consumer, loss after COMMIT.
- Откат feature flag без миграции сообщений и без изменения существующего WS-протокола.

## 6. Явные статусы

**УТВЕРЖДЕНО:** B, C как необязательное будущее, оба пилота как направление, сохранение действующей безопасности, отсутствие обязательной зависимости обычных действий от NATS.

**ПРЕДЛОЖЕНО:** 10s/2s polling, 60s overlap, схема subjects, отдельный server-side Go dispatcher, TLS + статические пользователи, CONFIG_FILE расширения, кратность coalescing 50ms. Требуют проверки при пилоте.

**НЕ УТВЕРЖДЕНО/НЕ РЕАЛИЗОВАНО:** SQL-триггеры NOTIFY, Go-клиент NATS, JetStream Economic, NATS RPC, новые API, запуск NATS как Windows Service по предложенной конфигурации.

Официальные свойства технологии: https://docs.nats.io/learn/core-nats/publish-subscribe , https://docs.nats.io/concepts/jetstream .
