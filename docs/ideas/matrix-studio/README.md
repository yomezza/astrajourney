# MATRIX × STUDIO — целевой UX космического терминала

**Статус:** решение владельца о направлении нового интерфейса (2026-11-19); **ещё не реализовано в production**. Это продуктовая спецификация для следующего исполнителя, а не разрешение изменять рабочую БД или выкатывать миграции.

**Источник общей концепции:** [командный терминал пилота](../pilot-command-terminal/README.ru.md), [архитектурный разбор](../pilot-command-terminal/02-frontend-architecture-prototype.ru.md), [правила репозитория](../../../AGENTS.md). Исходный UX-архив MATRIX × STUDIO передан владельцу в диалоге отдельно; его демонстрационные CSS/JS не являются production-реализацией.

## 1. Принятое направление

Объединить **Operations Matrix** (компактный, информативный космический интерфейс) и **Workspace Studio** (сохраняемые персональные рабочие пространства). Сохранить базовую палитру `web/styles/tokens.css` и реальные игровые возможности. Модульная структура должна оставаться расширяемой без увеличения постоянного меню.

**Неизменное решение владельца:** **ЧАТ и УВЕДОМЛЕНИЯ должны сохранить их ПРЕЖНИЙ production-стиль, поведение и функциональность.** Демо-реализация чата/уведомлений в MATRIX × STUDIO — **только иллюстрация независимой компоновки**; не использовать её CSS, DOM, fixtures, chat transport или demo notifications в настоящем клиенте. Стиль и логика: `web/features/chat/`, `web/styles/chat.css`, `web/features/notifications/`, `web/styles/notifications.css`. Оба модуля доступны глобально, могут оставаться открытыми **одновременно** с кораблём, картой и любым рабочим пространством, не исчезают при его переключении и не требуют перехода на отдельные страницы. Допускается адаптер размещения существующих окон/компонентов без визуальной переработки.

## 2. Рабочие пространства

- От **1 до 10** пространств на **аккаунт**, имя **1–32 графемы**, создавать, переименовывать, дублировать, переставлять, удалять (последнее удалить нельзя), выбирать стартовое и активное.
- Каждое пространство — независимая сцена со стабильным UUID, порядком вкладки, `ship_id` (контекст просмотра), набором **экземпляров** модулей с собственными UUID, расположением, размерами, порядком, сворачиванием, выбранными фильтрами/вкладками.
- Модуль может быть привязан к `workspace` (следовать кораблю пространства), `fixed` (конкретный авторизованный корабль) либо `none`; одинаковые названия кораблей не являются идентификаторами.
- Переключение пространства **не** меняет активный корабль на сервере и **не** запускает/прерывает полёт, добычу, торговлю, задание или передачу грузов.
- При отзыве доступа/продаже корабля показывать «Объект недоступен» и предложить выбрать заново; запрещена тихая подмена первым кораблём.
- Поддержать каталог доступных модулей с поиском/группами и добавление в пространство. Новые типы модулей регистрируются через единый контракт, с политикой контекста/состояния и прав доступа, а не копированием кода окон.
- Сохранять совместимость с `Modules` и её lifecycle (move, resize, minimize, maximize, pin, focus, loading, destroy, приватность). Существующая семантика pin **не равна** принадлежности пространству.
- Для узких экранов — переключаемая компоновка и доступный чат/уведомления, без горизонтальной прокрутки основного контента.

## 3. Глобальный слой связи — не часть workspace instances

```text
Terminal
├── GlobalCommunicationLayer (один экземпляр на авторизованный аккаунт)
│   ├── ExistingChatModule (production Chat, неизменный визуальный стиль)
│   └── ExistingNotificationsModule (production Notifications, неизменный визуальный стиль)
└── WorkspaceManager (1..10; server-persisted preferences)
    ├── Workspace A: контекст ship #A, окна 1..N
    └── Workspace B: контекст ship #B, окна 1..N
```

- Chat: сохранять реальные вкладки, избранное, глобальные/планетарные/секторные/корпоративные/личные чаты, модерацию, поиск, draft/focus и существующий transport. **Не создавать новое WebSocket-подключение на каждое пространство**.
- Notifications: реальный unread/read, фильтры, детали и массовая отметка остаются едиными для аккаунта; не клонировать серверные записи и не делать новый polling на каждую вкладку.
- Модули связи имеют независимые действия «открыть/скрыть», могут быть отображены рядом или поверх основной сцены, а во время перемещения/переключения рабочих вкладок не перезапускаются. На мобильных обеспечить переключаемые панели; полнота функциональности не должна пропасть.
- Глобальные элементы связи не включаются в сохранённый список экземпляров рабочих пространств и не должны удаляться вместе с пространством.

## 4. Где хранить настройки: backend-предложение, не утверждённая миграция

Выполнить аудит фактических схем PostgreSQL, миграционного runner Cosmic, пользователя/аккаунта и прав. **Если подходящего существующего хранилища нет**, добавить версионированные таблицы (имена лишь примеры, не действующие таблицы):

- `pilot_workspaces`: внутренний ID, owner user/account FK, display name, ordinal, контекст, `is_default`, timestamps.
- `pilot_workspace_modules`: ID экземпляра, FK workspace ON DELETE CASCADE, allowlisted module type, binding mode/fixed object, layout (x/y/w/h/width/span/minimized/pinned/z), ограниченный JSONB UI state, schema version.
- `pilot_workspace_preferences` или account-level record: active/default workspace, revision для optimistic concurrency, настройки вида глобальных dock'ов (только разрешённые UI preference поля).

Сначала оценить, нужны ли действительно три таблицы либо достаточно меньшей нормализованной схемы без потери инвариантов. Не смешивать account-owned state с server-authoritative game state. Ограничения 1–10, уникальности порядков/ID и безопасность владения должны обеспечиваться сервером/транзакциями, не только интерфейсом. Нужны индексы owner/ordinal и FK, ACL для любого ID и конфликтное обновление по revision/version; миграции обратимо совместимы с существующими пользователями. Не сохранять chat messages, текст личных диалогов, токены, балансы и API snapshots в workspace JSONB.

При первом входе создать одно стартовое пространство идемпотентно либо только при необходимости; определить способ мягкого переноса старых геометрий `Preferences` и не перезаписывать существующие пользовательские настройки.

## 5. API — сначала аудит контрактов

Предполагаемые операции (не объявляются существующими): получить список/активную раскладку, создать/переименовать/дублировать/переставить/удалить пространство, обновить состав/размеры/контекст/состояние окон, назначить стартовое и активное. Маршруты/DTO/ACL выбрать по существующим паттернам Cosmic/Web. Должны быть:
- изоляция по account/session; сервер валидирует owner каждого workspace и module instance;
- ревизии/etag или expected_revision; конфликт 409 без потери изменений; границы размеров и лимиты размера JSON;
- idempotency там, где повторная отправка команды может создать дубль; серверная валидация имен (Unicode graphemes), enum и context ID;
- минимизация write-amplification при drag/resize через debounce/batching, сохранение после отпускания; не делать SQL запись каждый кадр;
- на просмотр и на каждую бизнес-команду отдельно проверять права и актуальность ship; не перенаправлять действие на server active ship из-за одной UI-вкладки.

## 6. Обязательные сценарии приёмки

1. Две вкладки «Добыча #1» и «Добыча #2» с **двумя разными ID кораблей**, в каждой открыты корабль/добыча/трюм. Переключение сохраняет фильтры и контекст без реального выбора другого active ship.
2. Открыты **старый production Chat и старые production Notifications**, одновременно открыты карта и корабль. Изменение workspace, добавление/удаление окон, F5 не должны ломать их стиль, сетевой транспорт, статус прочтения и соответствующие UX-состояния.
3. 1→10→попытка 11-го, name 32/33 графемы, пустое имя, удалить последнее, параллельная запись из двух вкладок, повтор запроса и чужой workspace ID.
4. Logout/login другого аккаунта: прежние private DOM/state не видны, нет межаккаунтной утечки, прежний доступный layout восстанавливается после возврата к первому аккаунту.
5. Отзыв корабля, отказ службы Chat, конфликт сервера, пустая раскладка, 320px и широкий дисплей, RU/EN, клавиатура и сокращённая анимация.
6. Существующие игровые команды, окна, модалки, backend задачи, Chat/Notifications и Planet Mode не регрессируют.

## 7. Внедрение

Backend-разработчик отвечает за Go/API/DB и интеграционное выполнение задачи в рамках явно выданного поручения; при необходимости затронуть Web/JS — соблюдать `web/` архитектуру и сохранение production модулей. Начать от **актуального main** в собственной короткой feature-ветке; эта docs-ветка является handoff/review, а не местом слияния production. Сначала тестовая БД/миграции и адресные проверки, затем PR владельцу. Не применять SQL к рабочей БД и не делать deployment/merge/release без отдельного разрешения.
