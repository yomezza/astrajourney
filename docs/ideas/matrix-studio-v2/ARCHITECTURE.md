# Архитектура MATRIX × STUDIO 2.0

## Слои
MATRIX Shell — общая навигация, телеметрия, компактная панель запуска вместо длинного меню. STUDIO Workspace — сохранённые рабочие пространства. Module System — каталог, реестр, экземпляры и контейнеры. Global Layer — старые Chat/Notifications и независимые плавающие инструменты. Не менять production-стиль чата/уведомлений, транспорт, историю, unread, каналы, модерацию; не дублировать подписки. Сохранить SPA и Planet Mode.

## Модель предметной области
- Семейство (type): стабильный идентификатор общей задачи, например ship, inventory, navigation; единая регистрация, общие контроллеры/компоненты.
- Экземпляр (instance ID): уникальный UUID, независимые настройки, состояние, привязка. Разрешены несколько экземпляров одного семейства в одном пространстве, включая одинаковый подвид и разные объекты.
- Purpose: функциональная задача, отличная от оформления; выбор задачи/объекта определяет подвид автоматически.
- Binding: правило разрешения объекта (CONTEXTS.md).
- Variant: функциональный подвид по объекту, назначению и правам; не отдельное семейство и не режим размера. Не создавать отдельные registry entries на каждый подвид.
- State: состояние игры/доступности (полёт, добыча, загрузка, ошибка и т.д.); не подвид.
- Placement: сохранённая плитка или временное плавающее окно. Общая реализация содержимого, отдельный контейнер. Преобразование между ними не предусмотрено.
- Presentation: размер, таблица/сетка, внутренние разделы, фильтры — UI preferences, не подвиды.

## Рабочие пространства
1–10 на аккаунт, 1–32 графемы имени, до 16 экземпляров на пространство; последнее не удаляется. Сохранить создание, переименование, дублирование (новые UUID), порядок, активное и стартовое пространство. Основной корабль опционален; возможно пространство без корабля. Новичку одно готовое пространство с кораблём, навигацией, трюмом, активными операциями; операции пока старый инструмент/сводка до отдельного паспорта, не проектировать M008 в этой задаче. Не перезаписывать старые пользовательские раскладки. При отсутствии готового безопасного контракта стартового элемента согласовать переходный вариант. Удаление пространства удаляет только UI.

Плитки — компактные адаптивные панели в гибридной компоновке; изменение размеров не меняет функциональный подвид. На маленьких экранах — доступная одноколоночная/адаптивная компоновка, не перезаписывать desktop geometry. Конкретный алгоритм сетки и размеры — задача Frontend, без фиксирования пикселей здесь. Не копировать APEX буквально.

## Каталог
Один реестр и каталог с режимами «Добавить в пространство» и «Открыть плавающее окно». Показывать семейства, искать по названиям/назначению; выбирать нужный сценарий/объект, пропускать лишние шаги при однозначном контексте. Проверять допустимость размещения и доступа. Глобальные инструменты (финансы, профиль, руководство, корпорация, администрирование) могут в будущем входить в пространство согласно своим паспортам/правам. Список флота — глобальный инструмент поиска и выбора объекта, не постоянная плитка. Существующие инструменты вне первого этапа не удалять; обеспечивать доступ через каталог/совместимый адаптер.

## Технические границы
Frontend: Go-independent vanilla JS/HTML/CSS/SVG, реестр семейств и scoped controllers, общий resolver, lifecycle, UI containers, адаптеры API, I18n, без singleton target для команд. Backend: Go/PostgreSQL, авторитетное игровое состояние, проверки прав/действий, валидация type/purpose/binding/settings/layout, ревизии и миграция. Сервер не выбирает внешний вид. Возможности новой службы Economy не должны требовать изменения ядра Studio; не вводить её сейчас.

Пример структуры (не обязательные имена): web/features/studio/core/{registry,context,instance,lifecycle,layout}.js, modules/ship/{definition,controller,views/...}, modules/inventory/..., modules/navigation/..., catalog/, workspace/. Не создавать дублирующие копии бизнес-логики на каждый подвид/контейнер.

## Хранение
Действующие pilot_workspace_preferences (JSONB + revision) и pilot_workspace_ids — исходная основа. Предпочтительно развить формат версионированного документа, не создавать таблицу на каждый подвид. Формат v2, поля, migration/compatibility и DTO — предлагаемые технические решения Backend, согласовать с Frontend. Хранить только разрешённые UI preferences, стабильные IDs, привязки, назначение, геометрию, вкладки/сортировку; не хранить игровые snapshots, секреты, балансы, грузы, токены. Сохранять по завершении drag/resize и debounce, не каждый кадр. Проверять размер payload (текущий предел 64 KiB), ownership, UUID, лимиты, ревизии и отсутствие конфликтного затирания. Не отключать текущие ACL.
