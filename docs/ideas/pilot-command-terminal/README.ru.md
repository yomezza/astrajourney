# Astra Journey — единый командный терминал и персональные рабочие пространства

**Статус:** проектная идея / UX-концепция, не утверждённая к реализации.  
**Область:** браузерный интерфейс Cosmic, без изменений игровой логики.  
**Этап:** обсуждение → изолированный интерактивный прототип → решение о внедрении.  
**Ограничения концепции:** не более 10 рабочих пространств на игрока; название каждого — не более 32 символов.

## 1. Суть

Заменить растущий список модулей в боковом меню **единым командным терминалом пилота**. Главное в терминале — **вкладки рабочих пространств**, которые игрок создаёт и настраивает под свои занятия: полёты, добычу, торговлю, колонии, управление флотом.

Рабочее пространство — не ссылка на несколько модулей, а сохранённая **рабочая сцена**: набор экземпляров окон, их расположение и размер, выбранные объекты и правила связывания окон с контекстом. Переключение вкладки восстанавливает именно эту сцену.

Ключевой сценарий: в «Добыча — 1» открыт корабль «Пилигрим» с одним ID, а соседние «Добыча» и «Трюм» работают с этим кораблём. В «Добыча — 2» можно открыть **те же типы модулей**, но с другим кораблём (пусть он тоже называется «Пилигрим»). Выбор во втором пространстве **не перенастраивает окна первого**.

Цель — дать игроку собственные инструменты организации работы, не усложняя основные игровые действия. Это пока **идея для тестовой пробы**, а не основание менять production UI.

## 2. Каким видит терминал игрок

```text
┌──────────────────────── КОМАНДНЫЙ ТЕРМИНАЛ ────────────────────────────────┐
│ [Полёты] [Добыча — 1] [Добыча — 2] [Торговля] [+]       [Все модули] [⚙] │
├───────────────────────────────────────────────────────────────────────────┤
│ Пространство: Добыча — 1                 Контекст: Пилигрим · корабль #41 │
│ [+ Добавить модуль]  [Контекст ▾]                       [Упорядочить]     │
│                                                                           │
│ ┌─────────────────────────┐ ┌──────────────────────────────────────────┐  │
│ │ Корабль                 │ │ Добыча                                   │  │
│ │ Пилигрим · #41          │ │ Следует кораблю пространства: #41       │  │
│ │ [фиксировано: #41]      │ │ Месторождения / действия                │  │
│ └─────────────────────────┘ └──────────────────────────────────────────┘  │
│ ┌─────────────────────────┐ ┌──────────────────────────────────────────┐  │
│ │ Трюм                    │ │ Карта                                     │  │
│ │ Следует кораблю: #41    │ │ Контекст системы корабля #41            │  │
│ └─────────────────────────┘ └──────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────────────────────┘
```

Во вкладке «Добыча — 2» тот же набор модулей может быть привязан к кораблю #82. Числа и имена в схеме **условные**, не реальные игровые ID.

Рядом с рабочими вкладками есть каталог **«Все модули»** с поиском и короткими группами: «Космос», «Флот», «Добыча и торговля», «Владения», «Связь и помощь». Это каталог действий, а не возвращение к постоянному длинному сайдбару. Состав и доступность модулей определяются настоящим интерфейсом и правами игрока.

## 3. Рабочие пространства

### Правила

- На аккаунт — **от 1 до 10** пространств, включая начальное.
- У пространства есть устойчивый внутренний ID и собственное редактируемое название: **1–32 видимых символа**, без названия из одних пробелов. Поведение Unicode/эмодзи и подсчёта символов уточнить в прототипе.
- Вкладки можно **создать, переименовать, упорядочить, продублировать, удалить**, выбрать пространство, открываемое по умолчанию.
- Последнее пространство не удаляется без создания замены.
- Создание одиннадцатого пространства недоступно с понятным объяснением.
- Удаление пространства удаляет только его **настройки интерфейса**, не игровые корабли, задания и данные.
- При переключении сохраняются и восстанавливаются состояние и компоновка, без новой отправки игровых команд.
- У каждого пространства есть контекст объектов и набор **экземпляров** модулей, а не только список типов.
- Называемая пользователем функция «закрепить окно в пространстве» **не равна** существующему режиму `pinned` оконного менеджера (в нём закрепление влияет на перемещение). Нужны разные действия и подписи.

Первый запуск: одно обычное рабочее пространство, возможность добавить остальные; миграция уже открытых окон и старых настроек — отдельное решение, без потери старого пользовательского расположения.

### Каталог и размещение

«Добавить модуль» открывает поиск/каталог доступных модулей. Добавление создаёт экземпляр **в текущем пространстве**. Окно можно перемещать, изменять размеры, сворачивать, убирать из пространства. Перемещение/размеры сохраняются автоматически; отдельная кнопка «Сохранить компоновку» необязательна.

Игрок должен понимать, что удаление окна из вкладки не отменяет запущенную добычу или полёт.

## 4. Контекст объектов и связи между окнами

### Контекст пространства

Минимально полезный пример — `ship_id` (выбранный корабль). В будущем возможны `system_id`, `colony_id`, `station_id` **там, где соответствующие модули действительно поддерживают этот выбор**. Не нужно реализовывать все виды контекста в первой пробе.

**У каждого экземпляра окна два режима привязки:**

1. **Следовать пространству** (`workspace`): например, «Добыча» и «Трюм» используют `ship_id` активного пространства; смена корабля в нём обновляет только связанные окна этой вкладки.
2. **Конкретный объект** (`fixed`): модуль «Корабль» всегда показывает корабль с заданным ID, даже если общий контекст пространства изменился.

Для модулей без предметного контекста — режим `none`: например, руководство или общий список исследований. Не показывать бессмысленный переключатель «следовать кораблю» у каждой кнопки.

### Критичные принципы

- Ссылка на корабль — по **устойчивому ID**, не по отображаемому имени. Несколько корпусов «Пилигрим» различаются ID.
- **Контекст просмотра не равен серверному активному кораблю.** Открытие вкладки не должно само переключать корабль игрока в игровой сессии, начинать перелёт или добычу.
- Чтение, фильтры и UI-выбор можно менять локально. Действия с ресурсами, движением и заданиями должны выполняться только после проверки, что существующий API поддерживает **явное указание целевого корабля** и что сервер проверяет права и актуальное состояние. Если поддержка отсутствует, в прототипе показать **просмотр без действия** или явную недоступность, а не незаметно перенаправлять действие на другой корабль.
- Изменение игрового состояния (например, завершение задачи, перемещение корабля) приходит из действующих источников и обновляет подходящие окна, **не меняя их сохранённый выбор** без причины.
- Продаваемый, недоступный или потерявший права объект — понятное состояние «Объект недоступен», с выбором замены. Не переназначать тихо на первый доступный.
- Переключение пространств не создаёт вторых реальных игровых задач и не повторяет команды.

### Пример 2 вкладок

| Параметр | «Добыча — 1» | «Добыча — 2» |
| --- | --- | --- |
| `workspace.ship_id` | условный #41 | условный #82 |
| Окно «Корабль» | фиксировано #41 | фиксировано #82 |
| Окно «Добыча» | следует #41 | следует #82 |
| Окно «Трюм» | следует #41 | следует #82 |
| Переключение вкладки | не меняет #82 | не меняет #41 |

Отдельный вопрос для развития: один и тот же тип модуля дважды **внутри одной вкладки** (например, сравнение двух кораблей). Для первого прототипа достаточно повторного использования типа **между вкладками**; поддержку повторов внутри вкладки оценить отдельно.

## 5. Сохранение состояния

### Сохраняем клиентское представление

- список, ID, порядок и названия пространств;
- активную и стартовую вкладки;
- ID и настройки экземпляров модулей;
- координаты, размер, порядок слоёв, состояние свёртывания;
- `binding_mode`, `fixed_object_id` и контекст пространства;
- поддерживаемые самим модулем элементы UI: выбранная вкладка, фильтры, сортировка, поиск, выделенная запись, по возможности позиция прокрутки.

**Не сохраняем как истину** баланс, грузы, ресурсы, права, статус полёта, таймеры и результаты серверных операций. После возвращения в окно они берутся из свежих игровых данных. Пароли, токены, сессии и ответы API целиком в настройках не хранятся.

Нужен простой явный интерфейс снимка UI-состояния модуля: например, `captureState(instance)` и `restoreState(instance, state)`, с версией формата; это **предложение к проверке**, не обязательный рефакторинг всего frontend. Если модуль не поддерживает сохранение фильтров, он восстанавливает только доступный безопасный минимум.

### Где хранить

**Прототип:** локальное хранилище браузера через существующий `Preferences` с **разделением по аккаунту и версией схемы**. Не хранить всё глобально под одним ключом для нескольких пользователей браузера. Перезапуск страницы проверяет восстановление; отсутствие `localStorage` не должно ломать терминал.

**Будущая production-версия:** решить отдельно, нужна ли синхронизация между устройствами и отдельное серверное хранение. Для UX-эксперимента не создавать SQL-таблицы или API.

Изменения компоновки можно сохранять по завершении перемещения/изменения размера и с небольшим ограничением частоты записи. При переключении вкладок — фиксировать финальный снимок перед скрытием.

## 6. Важные ограничения реального кода

Состояние концепции сверено с текущими исходниками; это не уже реализованная функция.

- `internal/server/web/index.html` — текущий `#sidebar` со списком модулей, в том числе специальные «Колонии», «Верфи», «Карта текущей системы».
- `internal/server/web/features/shell/navigation.js` — обработка навигации, сворачивание боковой панели, `Modules.open(...)`.
- `internal/server/web/ui/windows.js` — `Modules.create(id,...)`, единый `windows = new Map()` **по ID модуля**, менеджер перемещения/размеров/закрепления, переключатель открытых окон.
- `internal/server/web/core/preferences.js` — локальное сохранение настроек.
- `internal/server/web/features/fleet/index.js` и `internal/server/web/features/mining/index.js` — существующие экраны используют селекторы текущей экспедиции/выбранного корабля (`d().ship` и близкие данные).
- `scripts/frontend-generation/` — отдельная безопасная демосреда с mock API.

**Следствие:** нельзя получить две независимые вкладки простым копированием DOM-окон или сохранением их координат. Необходимы отдельные `workspace_id`, `module_instance_id` и scoped контекст; текущий ключ окна только по `module_id` недостаточен. В первой пробе не требуется переписывать весь `Modules` — можно построить **изолированное доказательство концепта** с отдельными экземплярами и адаптерами для 2–3 модулей.

Нельзя менять глобальный `Session.data.expedition.ship` при переключении вкладок ради имитации независимости. Это создаст ошибочное управление чужим кораблём.

## 7. UX-поведение и крайние случаи

- Вкладки всегда доступны; при нехватке ширины — горизонтальная прокрутка или выпадающий список, не сжатие текста до нечитаемого.
- Активное пространство видно по названию и текущему контексту: «Корабль · Пилигрим (#41)».
- Явные маркеры экземпляров: «Следует пространству» / «Закреплён объект #…»; возможность сменить режим из меню окна.
- Свёрнутые и временно скрытые окна не теряют UI-состояния; запущенные серверные задачи продолжаются независимо.
- Окно с недоступным объектом остаётся в компоновке с сообщением и возможностью выбора нового объекта.
- Скрытые/неактивные вкладки не должны без необходимости содержать десять полноценных живых дубликатов тяжёлой карты.
- Проверить масштабируемость при 1–10 вкладках, RU/EN, узком экране, обновлении данных, входе/выходе из аккаунта.
- Административные и ограниченные модули — строго по текущим правам. Сохранённая ссылка не даёт новых полномочий.
- Смена языка не сбрасывает расположение и привязки; пользовательские названия не переводятся автоматически.

## 8. Первая интерактивная проба — только frontend

**Рекомендуемый путь:** отдельный эксперимент в `scripts/frontend-generation/` или существующей UI/UX-лаборатории.

Должно работать в браузере (на согласованных фиктивных данных):

1. Создать до 10 вкладок; переименовать (до 32 символов), удалить, дублировать, менять порядок.
2. Добавить в пространство из каталога модули «Корабль», «Добыча», «Трюм» и хотя бы один модуль без корабельного контекста.
3. Выбирать контекстный корабль пространства из **двух разных кораблей с одинаковым названием**.
4. Для экземпляра выбрать `workspace` или `fixed`; видеть фактический корабельный ID в каждом связанном окне.
5. Открыть те же типы модулей в **двух разных пространствах** с независимым выбором.
6. Перемещать/изменять размер окон; переключать вкладки; перезагрузить страницу — увидеть восстановленные сцены.
7. Удалить один корабль из mock-набора или отозвать доступ и проверить, что возникло явное пустое/ошибочное состояние.
8. Сохранить старый UI без изменений, обеспечить мгновенный возврат из эксперимента.

**Важно:** это доказательство независимости состояния и удобства навигации, **не полноценная переработка игры**. В mock можно демонстрировать операции и их привязку, но реальные команды Cosmic отправлять нельзя.

### Критерий успеха

Наглядный тест: переключаемся «Добыча — 1» ↔ «Добыча — 2» и видим два разных ship ID, разные настройки окон и состояния; выбранный корабль и фильтры первого пространства не теряются. Обновление страницы сохраняет сцену; данные сервера при этом не подделываются. Пользователь понимает, куда обратиться за редким модулем, без постоянного списка из десятков пунктов.

## 9. Предлагаемый порядок внедрения

1. **Сейчас — только концепция:** сохранить здесь UX-модель и ограничения.
2. **UX-прототип:** испытать вкладки, каталог, раздельный контекст, два одноимённых корабля и сохранение в браузере.
3. **Ревизия интерфейсных контрактов:** определить, какие реальные модули поддерживают собственный объект и безопасные действия; сколько кода затронет независимый экземпляр окна.
4. **Решение владельца проекта:** продолжать ли, какой вариант компоновки выбрать, нужен ли серверный sync.
5. **Постепенное внедрение**, только после отдельного разрешения, с совместимостью старого меню и существующего `Modules`.

На этом этапе **не менять** Go-службы, PostgreSQL, маршруты API, NATS, производственную боковую панель и установленную логику окон.

## 10. Вопросы, которые остаются открытыми

Это решения перед production, **не блокирующие запись идеи**:

1. **Плавающие окна или раскладка по ячейкам?** Начать с привычных перемещаемых окон внутри зоны терминала; сравнить с магнитным выравниванием или сеткой после пробы.
2. **Сохранение между устройствами?** В прототипе — локально на этом браузере; облачная синхронизация требует отдельного дизайна API/хранения.
3. **Где живут окна вне пространств?** Возможен «временный» глобальный слой для чата/уведомлений и одноразовых диалогов; решить отдельно. Не создавать 10 экземпляров чата.
4. **Как менять контекст пространства?** Выбор в заголовке вкладки — основной вариант. Стоит ли выбор в модуле «Корабль» менять общий контекст автоматически — проверить на прототипе; по умолчанию избегать неожиданных изменений.
5. **Сколько экземпляров одного типа в одной вкладке?** Между вкладками — обязательно; внутри одной — отдельное UX/техническое решение.
6. **Какие команды могут быть адресованы неактивному кораблю?** Нужен аудит текущих API и правил Cosmic; без него только просмотр или существующие явно адресованные операции.
7. **Как переводить прежние закреплённые окна в терминал?** Выбрать безопасную миграцию после утверждения концепта, сохранив старые `Preferences`.

## 11. Границы этой идеи

Эта папка — **концепция**, не подтверждение реализованной функции. В неё не входит разработка нового frontend-фреймворка, самостоятельного менеджера задач, серверных рабочих пространств или изменения прав.

**Главный принцип:** «Игрок сохраняет не набор открытых кнопок, а несколько независимых рабочих мест — каждое для своего корабля и своей задачи».
