# Planetary Fixes — согласованные решения и UX-сценарии

**Статус:** утверждённые продуктовые решения владельца игры.  
**Основа:** [01-idea-v1.ru.md](01-idea-v1.ru.md).  
**Назначение:** описание требуемого поведения для согласования frontend и игровой логики; не набор готовых HTTP/WS-контрактов.

## 1. Ответы на семь вопросов

| № | Вопрос | **Согласованное решение** |
|---|---|---|
| 1 | Что видно на планете | **Полноценная 2D-игра со своим собственным HUD**: персонаж, сектор, настройки и необходимые действия. Космический UI не остаётся обычной верхней панелью поверх игры. |
| 2 | Как работать с посадочным модулем | Щелчок издалека вызывает **автоматический подход**. **Такое поведение распространяется на другие объекты планетарной сцены**, а не только на посадочную площадку. |
| 3 | Что происходит при возврате | Персонаж завершает присутствие в планетарном режиме, загружается космический терминал, **корабль сохраняет своё прежнее положение и состояние**. Анимация взлёта отложена на будущее. |
| 4 | Что с космическими окнами | Все они **визуально скрыты**, но при возвращении сохраняются их расположение, размеры и состояние открытия. |
| 5 | Что с чатом | Чат доступен **в обоих режимах**, интерфейс допускает адаптацию к 2D-режиму; не плодить второй controller/соединение. |
| 6 | Как игрок возвращается | **Штатно через реальный посадочный модуль**; отдельный аварийный механизм нужен только для технических проблем, с защитой от обхода правил игры. |
| 7 | Когда показывать загрузочную заставку | **При высадке, возврате и переходах между секторами**, в стиле существующего «Подключение к серверу». |

## 2. Видимый сценарий: космос → планета

```text
КОСМИЧЕСКИЙ ТЕРМИНАЛ
  ├─ Игрок выбирает посадочную площадку и «Высадиться»
  ├─ Космические окна и их состояние сохраняются
  ▼
ЗАСТАВКА / ПЕРЕХОД
  ├─ «Высадка на планету»
  ├─ «Подключение к планетарной службе»
  ├─ «Подготовка планетарной локации»
  ├─ «Загрузка ресурсов (Грунт)»       progress
  ├─ «Загрузка ресурсов (Персонажи)»   progress
  ├─ ... только реально требуемые группы
  └─ Готовность активного визита + необходимой сцены
  ▼
ПЛАНЕТАРНЫЙ РЕЖИМ
  ├─ Canvas/2D-игра занимает основную страницу
  ├─ Собственный HUD, настройки, данные персонажа/сектора
  └─ Общий чат доступен в адаптированной оболочке
```

Не подразумевается настоящая смена URL/перезагрузка: это единый frontend, переключающий визуально активный режим.

Если ошибка произошла **до фактической активации визита**, нельзя самовольно считать игрока высадившимся. Если ошибка произошла **после успешного серверного входа**, нельзя просто показать космос как будто визита нет: необходимо предложить восстановление и корректно отображать реальное серверное состояние.

## 3. Видимый сценарий: выбор объекта → подход → взаимодействие

```text
НАВЕДЕНИЕ / HIT-TEST НА ОБЪЕКТ
  └─ Клиент распознаёт тип и доступный идентификатор
       ▼
ЩЕЛЧОК ПО ОБЪЕКТУ
  └─ Команда «Подойти к объекту»
       ▼
СЕРВЕРНАЯ НАВИГАЦИЯ
  ├─ Найти разрешённую достижимую точку возле объекта
  ├─ Проложить маршрут с учётом препятствий и прав
  └─ Выполнить движение в рамках серверной скорости
       ▼
ПЕРСОНАЖ ПОДОШЁЛ
  ├─ Объект доступен для взаимодействия → показать его действия
  ├─ Только природный объект без реализованного действия → ничего не выдумывать
  └─ Маршрут недоступен → понятная ошибка/маркер
```

**Согласовано:** щелчок по объекту означает команду подойти; это не команда «сразу взаимодействовать».

**Не согласовано и требует решения:** появляется ли меню автоматически после подхода или по второму клику/отдельной кнопке; как отменять подход; как выбирать точку у объекта сложной формы; к каким видам объектов/персонажей можно подходить; нужна ли синхронизация целей между секторами. Эти вопросы должен разобрать логический чат. Нельзя заменить новое правило голым действием «идти в точку центра PNG».

Щелчок по свободному проходимому месту по-прежнему означает перемещение в точку.

## 4. Видимый сценарий: возвращение через модуль

```text
2D-СЦЕНА / ПЛАНЕТАРНЫЙ HUD
  ├─ Игрок выбирает реальный посадочный модуль
  ├─ Если далеко — персонаж подходит к доступной точке
  ├─ В зоне взаимодействия открываются действия модуля
  └─ Игрок выбирает «Вернуться в космос»
       ▼
ЗАСТАВКА / ПЕРЕХОД
  ├─ «Возвращение в космос»
  ├─ Безопасное завершение визита и освобождение reservation
  ├─ Восстановление/обновление космических данных
  └─ Запуск UI космического терминала
       ▼
КОСМИЧЕСКИЙ ТЕРМИНАЛ
  ├─ Окна восстановлены
  ├─ Актуальные данные проверены/обновлены
  └─ Никакого автоматического взлёта
```

**Не гарантировать успешный возврат до подтверждения сервером.** Если планетарная служба недоступна, действующие механизмы fencing/lease/revoke должны остаться предметом архитектурной проверки. Нельзя выпустить корабль из reservation только вследствие закрытия браузерного Canvas.

## 5. Видимый сценарий: переход между секторами

```text
ТЕКУЩИЙ ПЛАНЕТАРНЫЙ СЕКТОР
  └─ Игрок достигает разрешённого перехода
       ▼
СУЩЕСТВУЮЩИЙ OFFER / ПОДТВЕРЖДЕНИЕ
  ├─ Сцена назначения может ещё готовиться
  ├─ Игрок может отменить предложение по правилам протокола
  └─ При подтверждении — серверная транзакция перехода
       ▼
ЗАСТАВКА СМЕНЫ СЕКТОРА
  ├─ «Переход в сектор …»
  ├─ «Подготовка локации»
  ├─ «Загрузка ресурсов (Природа)» [если требуется]
  └─ Завершение загрузки нужных ресурсов и сцены
       ▼
НОВАЯ ЛОКАЦИЯ
```

Не показывать новый сектор до получения подтверждения и соответствующей актуальной сцены/epoch. При ошибке/отмене восстановить предыдущую локацию, не создавать «пустую промежуточную планету». Архитектор должен решить, **в какой момент** выводится заставка (во время offer/preload или непосредственно после confirm), чтобы не блокировать необходимый игроку выбор «Продолжить / Остаться».

## 6. Загрузочный экран: фирменный стиль и прогресс

### Использовать существующий стиль

В `internal/server/web/index.html` уже есть `#startup-screen` и `.startup-card` с анимированным `.startup-mark`; стили — `internal/server/web/styles/terminal.css`. **Переиспользовать общий внешний вид и визуальные токены**, но не обязательно сам DOM-узел стартового экрана: он связан с boot/login lifecycle. Техническую реализацию выбирает frontend-архитектор с учётом отсутствия конфликтов.

### Информация на экране

При затянутой загрузке:

- Крупный заголовок **по типу перехода**: «Высадка на планету», «Возвращение в космос» или «Переход в сектор …».
- Текущая понятная стадия (проверка допуска / соединение / получение локации / подготовка ресурсов / вход).
- Для загрузки изображений **группа в скобках**, например **«Загрузка ресурсов (Вода и берега)»**.
- **Progress-bar**, отображающий достоверную измеряемую часть; можно показывать общий прогресс по известным необходимым ресурсам.
- Сообщение при ожидании службы и действия восстановления при сбое/тайм-ауте.

Не выводить список имён спрайтов, сетевых URL, секретных данных, raw ticket, cookie или авторизационных служебных подробностей.

### Понятные группы

| Группа | Содержимое для пользователя |
|---|---|
| **Грунт** | Поверхностные материалы и основы рельефа |
| **Вода и берега** | Вода, мелководье, береговая кромка, рябь |
| **Природа** | Деревья, кустарники, камни и прочий природный декор |
| **Персонажи** | Атлас персонажей и необходимые визуальные представления |
| **Посадочные объекты** | Реально присутствующая посадочная инфраструктура текущего сектора |
| **Маркеры и эффекты** | Цель, выбор, границы, пыль и другие эффекты |

**Это примерная классификация, не требование загружать все группы в каждом секторе.** Отображать только группы, действительно необходимые текущей сцене; повторный вход может использовать кеш.

### Прогресс честный, не анимационный обман

Если известны завершённые загрузки и необходимое число файлов — показывать измеримую долю готовности. Если доступна фактическая передача байтов — можно измерять и её. Если операция сервера не сообщает процент — показывать стадию с неопределённой анимацией вместо придуманного процента.

Для многогрупповой загрузки уточнить, как учитывать одновременные запросы, ошибки отдельного файла и кеш. Не показывать «100% / готово», пока минимально нужное содержимое реально не готово.

## 7. Аварии, реконнект и восстановление

| Ситуация | Ожидаемая UX-цель |
|---|---|
| Планетарный сервер ещё подключается | Заставка с понятной стадией; без ложного входа |
| Часть арта долго качается | Групповая загрузка, progress-bar, отмена/повтор при необходимости |
| Часть декоративных спрайтов недоступна | Правило допустимой деградации после оценки; не замалчивать ошибку |
| Переход сектора не подтверждён | Текущий сектор остаётся источником истины, разрешена отмена/повтор |
| WebSocket потерян после подтверждённого визита | Resume существующего визита, без нового персонажа |
| Перезагрузка страницы во время 2D-режима | Проверить `planet/visit` и определить правильный активный UI-режим |
| Игрок застрял и не может добраться до модуля | Контролируемая **аварийная процедура**, не обычная кнопка бесплатного возврата |
| Серверный возврат задержан | Ожидание/повтор со статусом, а не оптимистический показ свободного корабля |
| Наличие нескольких вкладок | Один действующий контроллер по существующему epoch/fencing; нет «клонов» |

## 8. Ограничения UX

- RU/EN локализация сообщений перехода и групп.
- Понятная работа на узких экранах, с изменением масштаба и клавиатурой; доступность индикатора прогресса.
- По возможности `prefers-reduced-motion` для анимации ожидания; не терять статусы.
- Не вводить второй дублирующий Chat-controller и не уничтожать личные черновики при смене режима.
- Не изменять серверную геометрию и публичные права ради визуальной плавности.
- Не дублировать CSS заставки; общий стиль — одно место в системе UI.

**Это согласованная UX-идея, а не утверждение, что любой из сценариев уже реализован.**
