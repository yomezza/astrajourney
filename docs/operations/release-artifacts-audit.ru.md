# Astra Journey — аудит хранения релизных бинарников (без миграции)

**Дата:** 2026-11-11.  
**Статус:** проверенная инвентаризация текущей схемы и предложение перехода; **не разрешение менять сборку или удалять файлы**.  
**Репозиторий:** `yomezza/cosmosimulator`, название игры **Astra Journey**.

## 1. Что обнаружено в `main`

Содержимое каталога `downloads/` по GitHub Contents API при проверке:

| Показатель | Значение |
| --- | ---: |
| Всего файлов | **112** |
| Исполняемых файлов `.exe` / `-linux-amd64` | **107** |
| Суммарный размер перечисленных бинарников в текущем дереве | **≈ 1 950,9 МиБ** |
| Исторических исполняемых файлов с префиксом `cosmosimulator` | **95** |
| Исполняемых файлов с префиксом `astra-journey` | **12** |
| Остальное | `SHA256SUMS` и четыре `*-build.json` |

Это **сумма размеров файлов текущего дерева**, а не точный размер `.git`, сетевого клона или всей истории; в Git могли остаться ещё более старые blob-версии. Из-за бинарников каждая новая версия увеличивает объём репозитория.

## 2. Почему нельзя просто удалить `downloads/`

Текущая инфраструктура **не только хранит**, но и использует эти файлы.

- [`scripts/build-release.py`](../../scripts/build-release.py) строит Windows/Linux amd64 для Cosmic, Planet, Chat, записывает их в `downloads/`, добавляет manifest `*-build.json` и обновляет `downloads/SHA256SUMS`. Скрипт запрещает перезапись уже существующего имени версии.
- [`.github/workflows/release.yml`](../../.github/workflows/release.yml) запускается на тег `v*`: выполняет `sha256sum -c downloads/SHA256SUMS`, проверяет наличие пар Windows/Linux и отправляет бинарники, manifest, конфигурационные примеры и контрольные суммы в **GitHub Releases**.
- [`.github/workflows/release-linux-backfill.yml`](../../.github/workflows/release-linux-backfill.yml) поддерживает исторический backfill Linux-файлов в старые релизы. Он также читает **локальные** файлы `downloads/` и проверяет прежние хеши.
- Release notes и, возможно, внешние ссылки/установщики могут ссылаться на содержимое `downloads/`. Перед переносом нужны аудит ссылок и проверка доступности файлов в исторических GitHub Releases.

Удаление каталога **сейчас** нарушит действующий workflow и, вероятно, совместимость backfill. Добавление файлов в `.gitignore` тоже не удаляет уже отслеживаемые Git-файлы.

## 3. Целевое разделение

- **Git `main`**: исходники, версия, конфиги-примеры, скрипты, workflows, текстовые release notes, проверяемая metadata сборки при необходимости.
- **GitHub Releases**: подписанные тегом сборки Cosmic/Planet/Chat для Windows/Linux, контрольные суммы и manifest сборки.
- **GitHub Actions artifacts**: временные промежуточные результаты CI, не долговременная публичная ссылка.
- `downloads/` на рабочей машине разработчика может оставаться **локальной выходной директорией** для инструмента сборки, но новые бинарники не обязаны попадать в Git.

Исторические файлы не трогать без отдельной проверки; существующие опубликованные теги и SHA нельзя подменять новыми сборками под старым именем.

## 4. Предлагаемая безопасная последовательность

1. **Проверить инвентаризацию**: собрать список релизов и их assets из GitHub Releases, сравнить теги/имена/размеры/хеши с архивом `downloads/` и источником сборки. Выделить версии без assets. Отдельно проверить прямые ссылки из README, конфигов и скриптов.
2. **Спроектировать выпуск без commit бинарников**: новые GitHub Actions должны по **точному Git-тегу/commit SHA** собирать все ожидаемые платформы и службы, фиксировать metadata и SHA256 **только текущего релиза**, затем публиковать assets. Сохранять проверку соответствия встроенных версий, Windows PE/Linux ELF и source cleanliness; рассмотреть `workflow_dispatch` для сухого прогона.
3. **Пилотировать на тестовом prerelease/теге**, не затрагивая существующие имена. Проверить повторный запуск, сохранность assets, невозможность незаметной перезаписи, доступность скачивания и полноту SHA/manifest.
4. **Одним согласованным изменением** обновить `scripts/build-release.py`, `release.yml`, нужные backfill-процедуры, `.gitignore`, инструкции и ссылки. Для старых релизов оставить совместимый путь восстановления. Не пытаться на промежуточном коммите одновременно удалить binaries и сохранить старые `sha256sum -c` на весь архив.
5. **Только после успешного выпуска и письменного решения владельца** убрать ненужные бинарники из **новых версий дерева Git**. Перед этим обеспечить доступность всех требуемых исторических assets и зафиксировать проверяемую карту перемещений.
6. **Не переписывать Git-историю автоматически.** Удаление файлов из текущего дерева **не уменьшает автоматически старую Git-историю**. Отдельная очистка истории меняет commit SHA, затрагивает теги, форки и старые ссылки и требует самостоятельного плана, согласования, резервного копирования и окна миграции.

## 5. Неизменяемые требования безопасности

- Нет автоматического удаления `downloads/`, переписывания тега или истории.
- Нет изменений действующих рабочих служб, БД или реального NATS.
- Обычные `go test ./...` и сборки остаются релевантными, но **для этого документа код не изменялся и тесты не запускались**.
- Итоговое решение по выпуску должно включать план отката и список затронутых workflow/скриптов, а не только экономию размера репозитория.

## 6. Следующее действие, требующее отдельной команды

Поручить backend/release-разработчику **только аудит доступности historical GitHub Release assets и проект нового CI-процесса**. Полную миграцию `downloads/` проводить отдельно, после проверки и согласования.

**Вывод:** около 1,9 ГиБ текущих бинарников дают серьёзную причину изменить процесс выпуска; переход возможен без потери истории и без изменения имени репозитория, но не простым перемещением каталога.
