# Backend 005 — внедрение MATRIX × STUDIO с серверными рабочими пространствами

**Роль:** ты backend-разработчик Astra Journey (Go + PostgreSQL + браузерный Web на vanilla JS). **Владелец выбрал MATRIX × STUDIO как направление переработки интерфейса и просит подготовить/внедрить backend, включая таблицы настроек игроков при необходимости.** Это явная задача для разработки; её реализация должна идти в новой feature-ветке, через проверяемый PR. Не merge/deploy/release без отдельной команды.

**Репозиторий:** https://github.com/yomezza/astrajourney  
**Ветка с согласованным UX-handoff и настоящим заданием:** `docs/matrix-studio-integration-handoff`  
**Каноническая спецификация:** `docs/ideas/matrix-studio/README.md` **в этой ветке**.  
**Ранее созданный автономный прототип:** архив `AstraJourney_MATRIX_STUDIO.zip`, переданный владельцу в ChatGPT. Он только визуальный/UX-референс; исходник из архива НЕ вставлять целиком в production. Если нет доступа к архиву, спецификация самодостаточна, запроси его для визуальной сверки.

## 0. Сначала изучи действующий main

Прочитай `AGENTS.md`, `README.md`, `docs/repository-organization.ru.md`, `docs/ideas/pilot-command-terminal/README.ru.md` и технический документ рядом, новую спецификацию выше, текущие `web/index.html`, `web/styles/tokens.css`, `web/styles/terminal.css`, `web/ui/windows.js`, `web/core/{preferences,session,snapshot-store}.js`, `web/features/{shell,workspace,fleet,mining,chat,notifications,planet}/` и реальные Go/SQL/HTTP contracts. Используй **актуальное расположение `web/`**: в старых документах могут встречаться исторические пути `internal/server/web/`. Изучи текущие migrations, схему учётных записей, ownership ship, security и tests до выбора имени таблиц или endpoints. Не выдумывай ID/структуры.

## 1. Главная цель и непреложные ограничения

Реализовать компактную оболочку Operations Matrix + настраиваемые рабочие пространства Workspace Studio. 1–10 пространств **на аккаунт**, название 1–32 графемы, создание/редактирование/дублирование/перемещение/удаление и стартовое пространство. Каждое пространство — независимый набор **экземпляров** модулей, свой ID выбранного для просмотра корабля, local UI state, geometry/layout/filters/binding fixed|workspace|none. Возможность расширять каталог новыми игровыми модулями.

**КРИТИЧЕСКИЙ UX-КОНТРАКТ: ЧАТ И УВЕДОМЛЕНИЯ ДОЛЖНЫ ОСТАТЬСЯ В СТАРОМ ДЕЙСТВУЮЩЕМ ВИДЕ.** Никакого копирования демо-чата и демо-уведомлений, их CSS/DOM/иконок из MATRIX × STUDIO. Переиспользовать production `web/features/chat/`, `web/styles/chat.css`, `web/features/notifications/`, `web/styles/notifications.css` — со старым визуальным языком, полным функционалом, обработкой read/unread, каналами, модерацией, transport. Оба — **независимые глобальные модули поверх/рядом с любой сценой**, их можно открыть **одновременно с картой/кораблём**, они остаются открытыми при смене рабочих пространств. Единственный Chat transport на аккаунт/браузерную сессию; никакого отдельного WS/polling для каждой workspace. Сохранить поведение Planet Mode.

Переключение рабочего пространства — **только просмотр**, не команда выбрать реальный active ship. Нельзя напрямую многократно монтировать singleton `renderShip`, `renderCargo`, `renderMining`, подменять `Session.data`, копировать DOM окон или направлять бизнес-команды на другой корабль. Любое действие должно иметь корректный server-authoritative target и проверку ownership; если действующий API не поддерживает явный ship_id, безопасно ограничить опасное действие до готового контракта, не маскировать под успех.

## 2. Backend / PostgreSQL

1. Аудит существующих tables/schema и миграций Cosmic; определить минимальную нормализованную модель для account workspaces, module instances и profile preferences. Новые таблицы **только если действительно нужны**. Примеры полей, FK и ограничений — в `docs/ideas/matrix-studio/README.md`. Выбрать реальные имена/схемы под проект.
2. Серверные limits: максимум 10, непустое имя до 32 Unicode-графем, нельзя удалить последнее; уникальность ID/ownership и порядка, валидные виды модулей, enum bindings, размер и схема allowlisted JSONB; versioned UI state. При удалении удалять только layout/UI, не корабли, задания или игровые сущности.
3. Отделить user-scoped prefs от игровых данных; server-owned user/account FK. При первой регистрации/логине — безопасная idempotent инициализация одного пространства и/или согласованный migration старого локального layout, без уничтожения старых настроек.
4. Блокировки или revision-based optimistic concurrency для правок/двух вкладок, безопасные повторы запросов, isolation of concurrent create/delete; не создавать рабочие пространства на каждый polling.
5. Реализовать документированный API в существующем стиле проекта: read/list, mutations create/rename/duplicate/reorder/delete, изменение контекста и состава/свойств модулей, default/active. Везде auth + user ownership + validation + 409 conflict, ограниченные payloads, отсутствие возможности читать чужие workspace ID.
6. На frontend внедрять оболочку итеративно через действующие `Modules`, `Session`, `I18n`, `Preferences`, `RequestScope` и API; сохранить RU/EN, a11y, responsive, безопасный logout, отказ/повтор соединения. Раскладка не должна переписать настоящие Windows/chat/notifications.
7. Не запускать SQL вручную в рабочей БД; миграции оформлять в реальном Go migration runner, проверять на новой и существующей **тестовой** БД. Безопасность и backup/preflight перед rollout.

## 3. Поэтапный рабочий процесс

A. Краткий архитектурный аудит: найдены реальные файлы/схемы, proposed schema/API, список неинстанцируемых singleton-модулей, способ сохранить Chat/Notifications и Planet. Зафиксировать факты против допущений.  
B. Backend + миграции + интеграционные тесты ACL/concurrency/idempotency/limiting.  
C. Frontend: совместимая оболочка, общий реестр экземпляров и глобальные production Chat/Notifications, read-only независимые Fleet/Cargo/Mining, затем безопасные мутации после проверки API.  
D. Регрессии и UX приемка по `docs/ideas/matrix-studio/README.md`, RU/EN, 320/1440 px, отказ/переподключение, restore, две разные ship ID.  

Если объем разумно разбить на несколько PR — начни с backend/схемы/контрактов и отдельно интеграции UI, но не сдавай только SQL без планируемой интеграции. Не менять модель экономики, права, Chat protocol, Planet geography, реальные игровые записи, секреты и релизные артефакты под видом UI-работы.

## 4. Чёткие критерии завершения

- После F5 и смены устройства у аккаунта восстанавливаются серверно сохранённые 1–10 workspaces и их UI-настройки; переключение между ними не меняет реальные игровые действия.
- Корабль A в вкладке A и корабль B в вкладке B не конфликтуют; ID, а не имена определяют target.
- **Чат/Уведомления в исходном оформлении**, оба доступны параллельно с кораблём, без потери unread, WebSocket и истории при switch.
- Сервер отклоняет чужие IDs, недопустимые данные и конкурентное затирание revision; в тестовой БД миграция проходит.
- Игровые API/миграции и старые настройки не ломаются, тесты и скриншоты сверены с production и концептом.

**Выпуск:** собственная feature-ветка от свежего main, PR **без автоматического merge**, отчёт со списком файлов, SQL схем/миграций, endpoint contracts, реально пройденными тестами, рисками и commit SHA. Если чего-то нет в доступных материалах, не угадывай и не объявляй готовым.
